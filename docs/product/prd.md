## 1. 背景与要解决的问题

- 坐轮椅、用助行器、手臂不方便或看不见的人，"这套房我能不能住"通常要等住进去才知道。门窄 5 厘米、冰箱门开不到位、床边没有转移空间，这些问题在户型图和效果图上都看不出来。
- 常见的评估方式是专业人员上门，按规范逐项量。结果依赖个人经验，成本高，也很难在买房、装修之前做。
- 家装设计软件能出好看的效果图，但不会告诉你"坐轮椅的人在这里转不了身"。
- 面向老人的居家适老化产品和服务已经很多。残障人士自己在买房、租房、装修前判断"我能不能住"的工具很少，而轮椅使用者对门宽、转身空间、够取高度的要求在各类住户里最严。

清先住要回答三个问题：

1. **这套房，这个人，能不能住？** 哪里过不去、哪里够不着，原因指到具体的门和家具，差多少厘米。
2. **怎么改？** 给出改造方案，可以是挪家具、换成某款真实商品、改门，也可以是整屋重新布置。
3. **改了有没有用？** 用同一套仿真再跑一遍，用数字证明。

## 2. 产品定位

**一句话：住进去之前，先替你住一遍。**

- **以残障人士为主角。** 数字住户首先是轮椅使用者、视障者和上肢受限者，助行器使用者（多为老人）是其中一类。用户首先是残障人士本人，其次是家属和改造设计师。
- 输入一张户型图和一句话需求，例如"我坐轮椅，下个月搬进这套房"。
- 系统把户型图变成可以仿真的 3D 户型，放进真实商品尺寸的家具，让"数字住户"完成日常生活任务。
- 输出无障碍体检报告、改造方案、前后对比和商品清单。
- 产品分两种模式：试住模式（Stay）看一套具体的家，解决具体问题；实验室模式（Lab）批量生成或导入大量住宅，做规模化验证（§2.3）。

和现有工具的区别：

| 对比对象 | 它们做什么 | 清先住多做的 |
|---|---|---|
| 家装设计软件 | 画户型、摆家具、出效果图 | 按真实身体尺寸和动作去"住"，找出用不了的地方 |
| 上门无障碍评估 | 人工按规范逐项量 | 买房、装修前就能做，结果可复现，可以批量做 |
| 规范检查清单 | 逐条对照门宽、通道宽 | 检查的是"完成一件事"能不能做成，比如开冰箱拿东西，不只是单个尺寸 |

卖点和背后的技术：

| 卖点（产品语言） | 背后的技术 |
|---|---|
| “每个问题都能指到具体家具，差多少厘米也说得清” | 规范条文变成可计算检查，违规按物体归因 |
| “按真实轮椅的长和宽来算，转身也算进去” | 矩形外形的 SE(2) 路径规划，加分层占用 |
| “你也可以自己坐上轮椅，在这个家里走一圈” | 自由步入：用键盘操控住户，身体外形在评估器同一份分层占用上实时检查碰撞 |
| “数字住户会想、会变通，还会说出来” | 大模型决策层加确定性运动层 |
| “改动最少的方案，改完马上验证” | 按代价排序的修复搜索，修复后重新仿真 |
| “商品页上的那件家具，先搬进你家试一试” | Lux3D 把商品图和参数做成能仿真的模型：按商品页尺寸校准，门扇扫掠、台下净空、把手高度从模型里量（§2.4） |
| “500 套户型一起体检，一个家具系列一次评完” | 实验室模式（§2.3、F8）批量运行；可选的方案演化模块输出一个可复用的修复函数 `propose(scene_ir, report, persona)`，返回排好序的改动列表，批量体检时直接调用（simulation §9.3） |
| “夜里起夜、着火疏散、地震也考虑” | 照度估算和烟气扩散的示意模型；交互原型里的火灾、地震降阶模型（F1 导入 3D 模型） |
| “万一倒下，担架抬得出去吗” | 同一个 SE(2) 规划器，换成担架外形 |
| “门口放个箱子也不怕” | 逐步加障碍的容错余量测试 |

### 2.2 创新点

竞品调研的检索范围内，下面三件事没有找到已有工作（[competitive-research §10.2](../research/competitive-research.md)）：

1. **规范条文当硬约束。** GB 55019 和 ADA 的门宽、转身圆、转移区、够取高度直接进评估器，每条结论带条文号。
2. **住户的身体真的去做一遍任务。** 轮椅（手动、电动、陪护推行）、助行器、上肢受限、视障的住户在带真实商品的家里完成入户、如厕、取冰箱、上床，按真实外形和转向约束判定。
3. **诊断到物体和厘米，改完重新仿真。** 问题指到具体的门和家具、差多少厘米；改造方案用同一套仿真复测，前后对比。

清先住把三件事接成一个闭环：户型 → 带真实商品的 3D 家 → 数字住户做任务 → 规范判定和归因 → 改造 → 复测对比。

产品功能和评分维度的对应（权重和证据见[比赛计划 §4](../../plans/hackathon-plan.md)）：

| 评分维度 | 产品上靠什么拿分 | 对应功能 |
|---|---|---|
| 群核技术栈（30%） | Lux3D 在判定主线上：把真实商品做成能仿真的模型，商品页没写的门扇扫掠、台下净空、把手高度从模型里量，过验证门后直接进判定（§2.4）；替换商品和辅具由 Lux3D 生成、校准、过 QA 后放进场景重新仿真；实验室模式里一个家具系列由 Lux3D 批量建模后评测；住户的人体、轮椅、助行器也由 Lux3D 生成并绑骨 | §2.4、F2、F5、F8、§5.6 |
| 有趣程度（25%） | 第一人称看轮椅卡在门口；评委打开 Demo 链接就能自己坐上轮椅走一圈；住户独白说出真实测量数字 | §5.7、§5.8、F4 |
| 创新性（20%） | 上面三点，配竞品对比页 | F4、F6、F7 |
| 完成度（20%） | 体检 → 归因 → 改造 → 复验一次走通；LLM 不可用时切规则模式；所有数字能在运行记录里查到 | §4、§11 |

对口的单项奖是空间设计、具身智能和功德无量（比赛计划 §5），界面文案和报告措辞围绕"户型改造""住户在物理场景里做任务""无障碍"三个词。主题是残障人士的居家无障碍，不做成适老化产品。

措辞：用"轮椅使用者""视障者""残障人士"这类说法。住户是自己拿主意的人，独白和画面写他自己怎么做、哪里被挡住，不写成被照顾的对象。

### 2.3 两种模式：试住模式和实验室模式

界面和英文材料里写作“试住 Stay”和“实验室 Lab”：Stay 是先住一遍，Lab 是在一大批住宅上做批量测试和对照实验。两种模式用同一套仿真和评估器。试住模式解决一套具体住宅的问题；实验室模式在大量住宅上做规模化验证。

| 项 | 试住模式 | 实验室模式 |
|---|---|---|
| 回答的问题 | 这套房、这个人能不能住，怎么改 | 一类户型、一个家具系列或一条设计规则，在大量住宅里对哪些住户好用、对哪些不好用 |
| 住宅从哪来 | 用户自己的家：户型图（F1），或已有的 3D 模型、扫描结果（F1 导入 3D 模型） | 批量生成：生成平面 → 转三维 → 摆家具（见下）；或数据集住宅（WSR 500 套整套住宅、SAGE-10k 单房间）；也可以上传一批户型图，走 F1 识别 |
| 家具 | 用户现有的家具，或"帮我布置"（F3） | 生成的住宅由 F3 按规则批量摆放；评测家具系列时，同一套平面分别摆基线商品和待测系列 |
| 住户 | 家里具体的人，可以调参数（§5.4） | 全部画像，可以对参数做扫描（例如轮椅宽 0.60–0.75 m） |
| 运行 | 交互式：对话、回放、自由步入；LLM 写独白和建议文字 | 批处理：只用规则策略，不调 LLM；场景清单、画像和种子固定，结果可复现 |
| 输出 | 体检报告、改造方案、前后对比、商品清单（F7） | 统计看板：任务成功率分布、失败原因排行、按房型和面积分组的问题分布、A/B 成对对比、最差案例列表；可导出全部 run 和汇总表 |
| 面向 | 残障住户本人和家属、无障碍改造设计师和服务商 | 科研人员、家具厂和品牌、开发商和设计院、标准研究 |
| 对应功能 | F1–F7 | F8，复用 F3 的布置和 F6 的评估 |

实验室模式生成住宅的链路：

1. **生成平面**：按户型分布（几室几厅、面积段、各房间面积占比、房间之间的邻接关系，统计自 WSR 500 套）和房间规则（入户门进玄关、卫生间挨着走廊或卧室）批量生成平面户型，输出结构 IR（房间、墙、门、窗），每个元素标 `source: generated`。门净宽、走廊宽这类设计变量按实验配置固定取值或扫描。
2. **转三维**：和 F1 户型图转 3D 用同一套规则（墙高 2.7 m、门高 2.1 m、窗台 0.9 m，按房间类型给地面材质），得到可仿真的场景和展示用 GLB。
3. **摆家具**：布局求解（F3）按房间功能摆必需家具：卧室有床和床头柜，卫生间有马桶和洗手盆，厨房有冰箱和灶台。按普通家庭的习惯摆，不预留无障碍空间，否则结果偏乐观；预留与否可以作为实验变量。
4. **体检**：模板补全后，对全部画像跑适用任务。

每一步都有几何检查：房间连通、每个房间能从入户门走到、面积在分布范围内、家具不穿墙不重叠。没过检查的住宅列进失败清单，不进统计。同一份实验配置（分布、变量、种子）重跑，生成的住宅和结果完全一致。数据集住宅跳过前三步，WSR 同时用来对照生成住宅的户型分布是否合理。

实验室模式的典型实验：

- **家具系列评测**：家具厂把一个系列（例如窄款冰箱、悬挑洗手台、低位吊柜）放进同一批典型住宅，和基线商品成对比较，回答"换成这个系列后，轮椅住户的 T3 成功率从多少变到多少，哪些户型反而变差"。
- **设计变量敏感性**：其他条件固定，只改一个住宅设计变量（门净宽、走廊宽、床侧留空），看各画像的任务成功率怎么变。评估器的判定阈值和评分规则不变（F6）。
- **研究数据和基准**：一批带任务结果和事件标注的住宅，可用于具身智能和建筑无障碍方向的研究，也用来检查评估器本身（步行对照成功率、同一输入重跑一致）。
- **户型库体检**：开发商、设计院、保障房项目上传自己的户型库，输出问题排行和户型之间的比较。

两种模式可以互相跳转：

- 实验室看板里点任一住宅，进入试住模式，看这套房的回放、问题列表和自由步入。
- 试住模式里的一套房可以"加入实验"：围绕它批量生成变体（换家具系列、改门宽、门口加杂物），看这套房在多大范围内仍然可用。

比赛里实验室模式以 WSR 500 套住宅为底（比赛计划 E9），加一组家具系列对比；生成链路先在一小批住宅上跑通“生成平面 → 转三维 → 摆家具 → 体检”（比赛计划 E19）。SAGE-10k 是单房间的生成场景（[data §7](../tech/data.md)），只作单房间批量测试的补充。

### 2.4 Lux3D 的核心作用：把真实商品做成能仿真的模型

商品页给的是图片和外包尺寸，判定要的不止这些：冰箱门开到哪里会挡住轮椅，洗手盆下面腿能不能伸进去，把手够不够得着。Lux3D 把商品页的图片和参数做成能参与仿真的商品模型，补上商品页没写、包围盒也判不了的几何。

| 判定要用的尺寸 | 商品页通常写不写 | 只有包围盒时 | Lux3D 模型给出 |
|---|---|---|---|
| 外包尺寸 W×D×H | 写 | 能判 | 不量取，以商品页为准，模型按它校准 |
| 冰箱、柜门的开启扫掠 | 不写 | 判不了 | 关节化后得到门扇半径和开启角度 |
| 洗手盆、书桌的台下净空 | 很少写 | 当成实心，轮椅脚踏和膝部伸不进去 | 从网格量出净空高度和深度 |
| 把手、操作面板的高度 | 很少写 | 判不了 | 从网格定位，进够取判定 |
| 床底、柜底的离地高度 | 不写 | 当成落地 | 从网格量出，进脚踏层占用 |
| 餐桌腿的位置 | 不写 | 判不了 | 从网格量出腿间距，判轮椅能否靠近 |

商品库里正好有这类缺口：S3 壁挂洗手盆的规格书没写安装后的台下净空，S5 小圆餐桌的腿布局没有公开数据，现在只能按假设算（`src/ha/assets/catalog.yaml`）。

- **取用顺序**：商品页或规格书写了的尺寸用商品页（`source: catalog`）；没写的用 Lux3D 模型的量取值（`source: lux3d`），报告里标“由模型量取，商品页未标注”；量取项没过验证门时用类目模板（`source: template`，标“基于模板假设”）。
- **验证门**：在商品页或规格书写了某项尺寸的商品上，比较模型量取值和标称值。每个量取项至少核对 2 件，误差都不超过 2 cm（自定）才放开用于判定（比赛计划 E18）。没过的量取项只用于画面。误差表进报告书。
- **试住模式**：改造方案推荐的替换商品是“真实商品加 Lux3D 补齐的几何”，换上后对所有住户重新仿真（F5、F6）。用户看到的是能买到的那件商品的外形。
- **实验室模式**：家具厂只需提供商品图和参数表，不用提供 3D 模型。Lux3D 批量建出整个系列，再放进同一批住宅评测（F8）。
- **住户角色**：住户的人体由 Lux3D 生成后自动绑骨，再从 Lux3D 公开动作库套上坐、推、走、够取等动作；轮椅、助行器、白杖由 Lux3D 生成，挂在角色的骨骼上。骨骼和动作只管画面，判定按画像的几何外形（§5.6 住户角色和动作）。

比赛聚焦资产生成，不做 Aholo World 的 3DGS 重建：3DGS 没有网格，不能当碰撞几何。

## 3. 用户

### 3.1 使用产品的人

| 角色 | 典型问题 | 他们最在意的输出 |
|---|---|---|
| 残障住户本人（C 端） | "我坐轮椅，这套房我能住吗？要改哪里？大概花多少钱？" | 一眼看懂的结论、改造清单、能买到的商品 |
| 家属 | "我妈刚开始坐轮椅，出院前家里要改哪里？" | 改造清单，和医院、康复机构给的轮椅型号对得上 |
| 无障碍改造设计师、服务商 | "给客户出一份有依据的改造方案" | 逐项依据（规范条文）、方案对比、可导出的报告 |
| 残联、社区的家庭无障碍改造项目 | "这批残疾人家庭各要改什么，改完达没达标" | 每户的改造清单，改造后复测作为验收依据，批量统计（实验室模式） |
| 家装、家居平台 | "推荐哪款商品，能让这个家变得可用" | 商品和问题的对应关系、换上之后的效果证明 |
| 地产开发商、设计院 | "这批户型里哪些对坐轮椅的人不友好" | 批量体检、问题排行、户型之间的比较（实验室模式） |
| 家具厂、家居品牌 | "我们这个系列放进普通人家里，坐轮椅的人用得了吗？比上一代好多少" | 系列和基线商品在同一批住宅里的成对对比，按画像和户型拆开（实验室模式） |
| 科研人员 | "要一批可复现、带标注的住宅和住户任务结果" | 固定场景清单和种子的批量 run、事件标注、汇总表（实验室模式） |

### 3.2 数字住户（被仿真的人）

6 个画像，加步行对照和担架。参数见 `src/ha/resident/personas.yaml`，每个数值都标了来源；技术参数见 [simulation §6](../tech/simulation.md)。

| 画像 | 一句话 | 主要风险 |
|---|---|---|
| 手动轮椅使用者 | 坐姿，车身宽约 0.70 m、长约 1.20 m，转身要大空间 | 门窄、通道窄、转不了身、高处够不着 |
| 电动轮椅使用者 | 坐姿，靠操纵杆驾驶，车身比手动轮椅更长更重 | 卫生间里转不了身、走廊转角、门口对不准 |
| 陪护推轮椅 | 陪护站在轮椅后面推着走，轮椅加陪护整体长约 1.7 m | 走廊转角、门口开门站位、卫生间里站不下两个人 |
| 助行器使用者 | 站姿慢行，双手扶助行器，不能同时开门；容易跌倒，夜里需要更亮（老人、下肢术后康复多属此类） | 门槛、开门、转弯余量、夜间看不清 |
| 上肢受限者 | 能走，但抬手和用力受限 | 吊柜、门把手、开关高度，冰箱门太重 |
| 视障住户 | 拿白杖探路，熟悉布局后沿已知路线走 | 白杖探不到的突出物（吊柜下沿、开着的柜门、墙上凸出物）、路线上临时放的东西 |
| 步行对照 | 普通成年人 | 作为对照组，说明“对普通人没问题的房子” |
| 担架 | 两人平抬的急救担架，长 1.90 m 加两端抬担架的人 | 卧室门口、走廊转角转不过弯（T7） |

- 电动轮椅和陪护推轮椅的判定方法和手动轮椅相同（真实外形、转向约束、转身空间），只是外形参数不同，和其他画像一起进 P0 基线。
- 陪护推轮椅按一个整体外形计算，不模拟陪护和轮椅各自怎么动。
- 视障住户要在评估器里新增"探测"判定（F4），P1 加入。

## 4. 主流程

一次完整使用分 7 步。演示视频按同样的顺序讲（见 §7）。

| 步 | 用户做什么 | 系统做什么 | 用户看到什么 | 对应模块 |
|---|---|---|---|---|
| 1 | 上传户型图，输入一句话需求 | 识别户型图；从需求里抽出住户类型、关注点和预算 | 户型图上叠加识别出的房间、门、窗，以及"我理解的是：轮椅使用者，关注卫生间和卧室"的确认卡片 | F1、意图解析 |
| 2 | 确认或修改识别结果（拖动门的位置、改房间名、改尺寸） | 生成 3D 户型（墙、门、窗、地面） | 3D 白模从户型图上"长"出来 | F1 |
| 3 | 选择"按现有家具"或"帮我布置" | 从家具库里选真实商品，按房间功能摆放 | 家具逐件落位，每件挂商品卡（品牌、型号、尺寸、价格） | F2、F3 |
| 4 | 点"开始试住" | 数字住户依次完成生活任务；运动层记录碰撞、卡住、够不着 | 第一人称或俯视回放，住户独白，碰撞点闪红，时间线上标出事件 | F4 |
| 5 | 看体检报告 | 汇总违规，按物体归因，给出差多少厘米和规范条文 | 总分、红黄问题列表；点一条问题，相机飞到现场 | F4、F7 |
| 6 | 点"帮我改"，可以选"小改"或"整屋重新布置" | 修复 Agent 生成 1–3 个方案，每个方案都对所有住户重跑仿真 | 方案卡：改了什么、花多少钱、分数从多少到多少 | F5、F6 |
| 7 | 选一个方案，看前后对比，导出 | 生成报告 PDF 和商品清单 | 左右分屏同步回放；商品清单带购买链接 | F6、F7 |

三条支线：

- **追问**：任何一步都可以在对话框里提问，例如"如果把门改成推拉门呢"。系统把问题转成一次编辑，重跑仿真后回答，并在 3D 里显示变化。
- **换住户**：同一套房可以切换住户（手动轮椅、电动轮椅、陪护推轮椅、助行器、上肢受限、视障、步行对照），也可以"全家一起评估"，报告按住户分栏。
- **自己走一遍**：第 4 步之后的任何时候都可以切到"自由步入"，用键盘操控当前住户在家里走、开门（§5.4）。手动操作暂停任务回放，不计入体检报告。

## 5. 交互设计

### 5.1 页面结构

单页应用。全局导航有首页、试住、实验室、素材库四项（§2.3、§5.10.2）。下面是试住模式的布局：三栏，左栏是对话，中间是 3D 视图，右栏是当前步骤的详情，底部是仿真时间线。实验室模式的界面见 §5.9。

```text
┌────────────┬───────────────────────────────────────┬──────────────────┐
│ 对话面板   │ 3D 视图                                │ 详情面板          │
│            │                                       │                  │
│ 用户：我坐 │ [俯视][跟随][第一人称][步入][分屏对比] │ ▸ 户型识别        │
│ 轮椅…      │                                       │   房间 6 / 门 7   │
│            │        （户型 3D、住户、轨迹、          │ ▸ 家具清单        │
│ 清先住：我 │          违规高亮、热力图）             │   23 件 / ¥18,420 │
│ 理解的是…  │                                       │ ▸ 体检报告        │
│ [确认][改] │                                       │   58 分 · 红 3 黄 5│
│            │   图层：□余量热力 □门扫掠 □交互区       │ ▸ 改造方案        │
│ ……         │         □夜间照度 □烟气               │   A / B / C       │
│            │                                       │                  │
│ [输入框]   │                                       │                  │
│ [+户型图]  │                                       │                  │
├────────────┴───────────────────────────────────────┴──────────────────┤
│ 时间线  T1 入户 ──●──── T2 卫生间 ──✕──── T3 冰箱 ──●── T4 转移 ──✕── │
│         住户：[轮椅▾]   速度：1x  ▶ ⏸                                  │
└───────────────────────────────────────────────────────────────────────┘
```

- **对话面板**：所有操作都能用一句话完成，也都有对应按钮。Agent 的每条回复带"卡片"，卡片上有可点的按钮（确认、修改、看现场、应用方案）。
- **3D 视图**：五种视角。俯视看全屋和图层，分正交的平面分析和透视两种；跟随在住户身后；第一人称在住户眼高（坐姿 1.2 m，站姿 1.6 m）；步入是用户自己操控住户；分屏对比左右放改造前后。默认俯视，住户开始动后切到跟随。点击任何物体，显示它的尺寸、来源（户型图识别 / 商品库 / 模板补全）和相关问题。
- **详情面板**：按流程分段折叠，当前步骤自动展开。
- **时间线**：每个任务一段，绿点是成功，红叉是失败，黄色三角是余量不足。拖动时间线，3D 回放同步跳转。

### 5.2 自然语言输入

用户可以随时用一句话驱动系统。意图解析 Agent 把输入转成结构化请求，**先回显理解结果，用户确认后才执行**。涉及花钱或改动方案的请求一律要确认。

| 用户说 | 解析结果（示意） | 系统动作 |
|---|---|---|
| "我坐轮椅，下个月搬进来" | `{residents:[wheelchair], focus:[], deadline:"1 month"}` | 选轮椅画像，跑全部适用任务 |
| "我妈用助行器，晚上经常起夜" | `{residents:[walker_elder], focus:[T6]}` | 选助行器画像，T6 夜间起夜排在最前 |
| "全家：我坐轮椅，我老公和孩子走路" | `{residents:[walking_control×2, wheelchair]}` | 三个住户都跑，报告分栏 |
| "卫生间能不能用？" | `{scope:{room:bathroom}, tasks:[T2]}` | 只跑和卫生间相关的任务 |
| "冰箱换个窄一点的" | `{edit:replace, target:refrigerator, constraint:{w_max_m:<当前宽度}}` | 从家具库找候选，重跑 T3 |
| "预算 2 万以内，不想动墙" | `{budget_cny:20000, forbid:[door_widen, wall]}` | 修复搜索加约束 |
| "整屋帮我重新摆一下" | `{repair_mode:relayout}` | 进入整屋重新布局 |
| "如果门改成推拉门呢？" | `{what_if:{edit:door_to_sliding, door:<当前选中>}}` | 只做一次假设编辑，结果标"假设" |
| "为什么说卫生间不行？" | `{explain:{task:T2}}` | 不重跑，按违规记录解释并跳到现场 |

规则：

- 指代消解靠当前选中对象。"这扇门""这个柜子"指 3D 视图里选中的物体；没有选中时追问"你指的是哪扇门？"，并在 3D 里把候选高亮。
- 数字和画像参数不由 LLM 生成。用户说"我腿脚不好"这类模糊描述时，系统给出可选画像让用户挑，不自行编造参数。
- 用户说的尺寸（"门 80 宽"）作为户型修正写入 IR，标 `source: user`，优先级高于识别结果。

### 5.3 自然语言输出

Agent 回复有三类，每类都有固定结构，数字全部来自仿真结果。下面的卡片是示例。

**结论卡（体检后）**

> 这套房对你爸来说**有 3 处过不去**，总分 58。
>
> 1. **卫生间门净宽 0.72 m**，轮椅需要 0.80 m，差 8 cm。轮椅在门口卡住，T2 卧室到卫生间失败。[看现场]
> 2. **主卧床右侧只有 0.65 m**，床边转移需要 1.20 m（GB 55019 3.4.6），T4 上下床失败。[看现场]
> 3. **冰箱门开到 70° 就碰到轮椅脚踏**，冷藏层能够到，但要侧身。[看现场]
>
> 另有 5 处余量不足（黄色）。要我出改造方案吗？[小改] [整屋重新布置]

**住户独白（回放时字幕）**

> "门太窄了，左边擦着门框……还差 8 厘米，我过不去。"
> "床这边太挤了，轮椅贴不过去，我没法自己上床。"

独白由决策层 LLM 生成，必须引用运动层给出的数字，程序校验不一致就改用模板句（[simulation §7.3](../tech/simulation.md)）。

**方案卡（修复后）**

> **方案 A · 小改（¥1,860）**：58 → 86 分
> - 主卧床向左平移 0.55 m，右侧转移区达到 1.20 m（T4 失败 → 成功）
> - 卫生间门改推拉门，净宽 0.72 → 0.84 m（T2 失败 → 成功）[商品：XX 推拉门套件 ¥1,280]
> - 冰箱换成 55 cm 宽的窄款双门冰箱 [商品：Siemens KD25NVL3AK]
>
> 其他住户：助行器使用者适用任务全部仍然成功，没有变差。[看前后对比] [应用]

每张方案卡都写明"其他住户有没有变差"，因为修复必须对所有住户重新评估。

### 5.4 关键交互细节

| 交互 | 行为 |
|---|---|
| 点违规"看现场" | 相机飞到问题位置，住户回放跳到出事那一帧，问题物体描红，旁边标出"实测 0.72 m / 要求 0.80 m" |
| 拖动家具 | 松手后 1 秒内只重跑受影响的任务（L0–L2），局部余量热力图实时更新；完整重跑在后台排队 |
| 余量热力图 | 地面按"住户还剩多少余量"着色：红 < 0、橙 0–5 cm、黄 5–10 cm、绿 > 10 cm。切换住户时热力图跟着变，直观看到"同一条走廊，人走得过、轮椅过不去" |
| 门扫掠图层 | 每扇门画出开启扇形；扇形和家具、住户重叠的部分标红 |
| 外形对比 | 同一扇门上叠加"圆盘近似"和"真实轮椅矩形"两个结论，说明为什么普通检查会漏判 |
| 前后对比 | 左右分屏或滑块；两边住户同步回放；底部并列两条时间线 |
| 商品卡 | 尺寸、价格、来源链接、抓取时间；"为什么选它"一句话（例如"宽 55 cm，比原冰箱窄 28 cm，开门不再碰脚踏"）|
| 改造清单 | 可以逐项勾掉，勾掉后自动重跑，分数实时变化，让用户自己权衡"哪项最值" |
| 点格子看原因 | 点余量热力或碰撞图层上的格子，打开格子详情：累计接触次数、受阻次数、涉及的家具或墙体、住户外形宽度、发生时间段，选中的格子加红框。接触记录写的是实际碰到的物体；受阻记录写的是住户停下的位置和附近物体，标"附近物体只用于定位" |
| 事件列表 | 按时间列出全部事件，图标区分接触、受阻、够不着、开门失败。点一条，相机飞到现场并打开对应格子的详情 |
| 任务勾选和预测表 | 住户卡下勾选要跑的任务，至少留一个。先出一张预测表：每个任务能完成还是受阻、预计耗时、第一个问题；点"执行"后按真实轨迹播放。每个任务独立重置起点和门的开关状态 |
| 调整住户参数 | 住户卡上"查看 / 调整参数"：身体宽度、外形长度、速度、水平够取距离、最高够取高度、开门力上限。默认值取 `personas.yaml`；改过的住户标"自定义"，报告里单列它的参数，和标准住户的结果分开。用于康复机构给出了具体轮椅尺寸的情况 |
| 开门动画 | 住户开门时门扇按开向转到位；开门失败时门扇停在被挡住的角度，挡住它的物体描边 |
| 播放控制 | 暂停、1× / 2× / 4× 倍速；暂停时视角照常可以操作；页面切到后台时自动暂停 |
| 导出 | PDF 报告（结论、问题、方案、前后对比截图、规范依据、商品清单）；分享链接（只读 3D）；运行包 JSON（住户参数、任务、动作、事件、修复候选记录、前后两版场景参数）；栅格 CSV（每格的坐标和余量，可导入 Excel 或 GIS） |
| 自由步入 | W / S 前进后退，A / D 按画像的转向速度转身，鼠标拖动转视角，E 开关附近的门。身体外形碰到障碍就停住，碰到的物体描边，屏幕角落实时显示"左侧余量 3 cm"这类数字。手动操作不进报告，右上角标"体验模式" |
| 外形叠加 | 绑骨住户模型上叠加评估器用的矩形或圆盘外形（半透明），一键开关，说明"判定按这个外形算" |
| 修复过程 | 方案卡下展开"试过的改法"：每个候选写改了什么、重跑后各任务的结果、采纳或淘汰的原因。没修好的任务继续显示失败，并列出试过的改法 |
| 方案切换和还原 | 任何时候都能在原始户型和各方案之间切换，切换后 3D、报告、时间线一起变；"还原"回到原始户型 |
| 商品卡生成状态 | Lux3D 生成的商品在卡片上显示状态：生成中、尺寸已校准、QA 未过（用包围盒加主图）。点开能看首次生成、尺寸校准后、入库三版对比。模型量取的尺寸带“模型量取”标记，悬停显示它在验证门上的误差 |
| 住户状态气泡 | 住户头顶显示一句短状态（通行中、等待、出口受阻、避烟、已安全），和独白字幕并存：气泡说"在干什么"，字幕说"为什么" |
| 渲染风格 | 两种：实景（GLB 原有材质，用于视频和首页）和诊断（白模加墨色描线，分析图层画成地面标线，用于分析和报告插图）。只换材质和图层，不改几何和判定，详见 §5.10.11 |

### 5.5 不确定和出错时怎么提示

- **户型识别不确定**：置信度低的门、窗、尺寸标黄，要求用户确认。没有比例尺的户型图，要求用户给出一个已知尺寸（例如"入户门 0.9 m"或某面墙的长度）。
- **家具尺寸来自模板**：商品卡上标"尺寸为估计值"。
- **任务不适用**：例如户型里没有冰箱，T3 显示"不适用"，不算失败，并提示"要不要放一个冰箱再测？"
- **担架、烟气、夜间照明**：结果标"示意分析"，报告里写清假设。
- **LLM 不可用**：独白改用模板句，界面右上角显示"规则模式"，其他功能不受影响。
- **长任务**：整屋重新布局、批量体检显示进度条和阶段名（"生成候选布局 3/8""重跑仿真 12/24"），可以取消。

#### 住户角色和动作

流程：Lux3D 文生 3D 生成一个全身人体角色 → `animations/rig` 自动绑骨 → `animations/retarget` 一次套上下表的 10 个动作（combined 模式，一个 GLB 里多个动画片段）→ three.js `AnimationMixer` 按运动层的动作序列切换片段，角色沿轨迹移动。所有画像共用这一个人体角色，陪护也用它；画像之间的区别在道具和动作。道具由 Lux3D 生成并挂到骨骼上：手动轮椅（S9）和电动轮椅挂在髋部，助行器（S10）跟随双手，白杖挂在右手。电动轮椅和白杖还没进 `catalog.yaml`。

| 运动层动作或事件 | 动作片段（Lux3D 公开动作库 ID） | 画面 |
|---|---|---|
| 轮椅移动（手动） | `Sitting_Idle_Loop` | 坐在轮椅上前进。动作库没有推轮圈动作，手臂推轮由前端按轮速程序化叠加，来不及做就只保留坐姿 |
| 轮椅移动（电动） | `Driving_Loop` | 坐姿，手放在前方，当作握操纵杆 |
| 陪护推轮椅 | 陪护 `Push_Loop`，住户 `Sitting_Idle_Loop` | 两个角色一起沿轨迹移动 |
| 助行器行走 | `Push_Loop` | 双手推着助行器慢走 |
| 视障者行走 | `Walk_Loop` | 白杖左右扫动由前端转动手腕骨骼实现，探到突出物时停住并标出 |
| 上肢受限者、步行对照行走 | `Walk_Loop` | — |
| 开门、按开关、开冰箱 | `Interact` | 伸手操作 |
| 够取（`reach`） | `PickUp_Table` | 手伸向目标；够不着时手停在画像够取上限的高度，手和目标之间标出差值 |
| 床椅转移（`transfer`） | `Sitting_Exit`、`Sitting_Enter` | 从轮椅起身，坐到床边 |
| 放弃（`give_up`） | `Idle_No_Loop` | 摇头 |
| 求助（`request_help`） | `Idle_TalkingPhone_Loop` | 打电话求助 |

- 骨骼和动作只用于画面。成败、余量、够取差值都来自评估器；手停在哪里按评估器给的数字摆，不用动画判断够不够得到。
- 积分：人体文生 3D 1 次、rig 1 次、retarget 1 次。rig 和 retarget 的单价以 quote 为准，create 前在群里确认（[aholo-lux3d §3](../tech/aholo-lux3d.md)）。
- 生成后在网页里逐个片段检查（比赛计划 E7）。不合适的片段退回原型 `js/avatars.js` 的程序化人物、轮椅和助行器，再不行用方盒和圆柱，外形叠加层照常显示。

- **场景集**：选来源（数据集、上传的户型库、批量生成），再按房型、面积、有无某类家具筛选。选批量生成时填户型分布（几室几厅、面积段）、套数和种子，生成后可以抽看平面图、3D 和家具摆放，没过几何检查的单独列出。显示筛掉了多少套、为什么筛掉。

- **导出**：汇总表（CSV）、全部 run 目录、实验配置（场景清单、画像参数、变量、种子），别人拿到配置能重跑出同样的数字。

### 5.10 前端设计

本节是现场段网页的定稿设计，覆盖页面、交互、视觉、渲染、代码和资产。和 §5.1–§5.9 冲突时以本节为准。

#### 5.10.1 原则

- **一屏一个问题**：每一步只回答用户当下的一个问题（这套房是什么样、谁来住、住得下吗、哪里不行、怎么改、改完好在哪），其余信息收进面板。
- **真实渲染，真实仿真**：画面用物理渲染，火和烟、门、住户运动都用仿真结果驱动；成败和分数只来自评估器（§5.10.12）。
- **符合 POUR**：
  - 可感知：状态同时用颜色和图案表达，色盲也能分辨；正文对比度不低于 4.5:1；住户独白有字幕。
  - 可操作：所有功能都能用键盘完成；闪烁不超过每秒 3 次（WCAG 2.3.1）；系统设置了"减少动态效果"时关掉镜头运动和文字绕排动画。
  - 可理解：白话写文案，同一件事全程用同一个词；出错时说清楚怎么改。
  - 健壮：语义化 HTML，进度和结论用 ARIA live 播报；WebGPU 不可用时退到 WebGL2，路径追踪失败时留在实时档。

```text
└────────────────────────────────────────────────────────────────────────────────────┘
```

- **步骤栏**：户型 → 住户 → 试住 → 体检 → 改造 → 对比。每一步前面是一个盲文点位，走过的步骤点位填满（§5.10.11）。可以点回前面的步骤；后面的步骤在前置完成前不可点，悬停说明还缺什么。
- **场景切换**：白天跑 T1–T4，夜间跑 T6，起火跑 T5。担架（T7）是住户，在住户步骤勾选。
- **画面风格**：实景和诊断两种，只换材质和图层，不改几何和判定（§5.10.11）。
- **视角**：俯视、跟随、第一人称、步入。步入是视角，不是步骤，任何步骤都能切进去，手动操作不进报告。
- **楼层切换**：单层户型不显示；两层户型放到线上段。
- **图层菜单**：通行余量、风险点、门扫掠、判定外形（§5.10.5）。
- **面板**：左右面板都能收起。收起后用 `camera.setViewOffset` 把画面中心移回屏幕中央。录制模式隐藏左右面板，只留字幕和时间线（§5.10.13）。
- **时间线**：只在试住和对比两步显示，每位住户一条泳道。绿点成功，红叉失败，黄三角余量不足；形状不同，不只靠颜色区分。
- **图签**：右下角，写户型名、住户、场景、方案，带比例尺和北向，截图和报告直接可用。
- **键盘**：1–4 切视角，空格播放或暂停，←/→ 逐事件跳转，回车确认当前卡片，Esc 退出步入或关闭弹层，Tab 在面板之间移动。

| 步骤 | 用户的问题 | 3D 视图 | 右栏 | 对话卡片 | 主按钮 |
|---|---|---|---|---|---|
| 户型 | 这套房识别对了吗 | 平面图升起成白模，材质铺开 | 房间、门、家具清单，低置信度标黄 | 意图卡 | 确认户型 |
| 住户 | 谁来住 | 住户站到入户门口 | 住户卡分组（§5.10.4），勾选任务 | 住户确认卡 | 开始试住 |
| 试住 | 他们住得怎么样 | 跟随回放，失败处镜头推近 | 当前任务和实时余量 | 独白字幕 | 看体检 |
| 体检 | 哪里不行、为什么 | 俯视，问题点脉冲标记 | 分数和问题列表，点一条飞到现场 | 结论卡，Pretext 讲解 | 帮我改 |
| 改造 | 怎么改最划算 | 方案里的家具补间到新位置 | 三张方案卡和散点图（§5.10.6） | 方案卡 | 应用方案 |
| 对比 | 改完好在哪 | 左右分屏或滑块，同步回放 | 前后分数和每项变化 | 对比卡 | 导出报告 |

**上传卡**：演示用 H1 的平面图（从 IR 画出的标准户型图）。识别结果叠加在图上，标"示意"；F1 接入后换成真实识别结果。用户确认后平面图升起成 3D。

#### 5.10.4 住户

住户数量不设上限，一家人每人一张住户卡，每人一条时间线泳道。住户卡按三组排列：

| 分组 | 住户 | `personas.yaml` | 道具和画面 |
|---|---|---|---|
| 行动 | 手动轮椅 | `wheelchair` | 轮椅（S9）挂髋部 |
| 行动 | 电动轮椅 | 待加 | 电动轮椅挂髋部，`Driving_Loop` |
| 行动 | 陪护推轮椅 | 待加 | 两个角色一起移动，外形按轮椅加陪护算 |
| 行动 | 助行器 | `walker_elder` | 助行器（S10）跟随双手 |
| 行动 | 上肢受限 | `upper_limb` | 无道具，够取范围缩小 |
| 视觉 | 视障 | 待加 | 白杖挂右手左右扫动；遇到白杖探不到的突出物（离地高于杖尖、低于头部）时停住并标出 |
| 急救搬运 | 急救担架 | `stretcher`（carriers） | 两名抬担架的人加担架，跑 T7 |

- 步行对照（`walking_control`）只用来校准评估器，不放进住户卡，在设置里打开。
- 角色、绑骨和动作对应见 §5.6 的"住户角色和动作"。
- 电动轮椅、陪护推轮椅、视障三个画像要加进 `personas.yaml`，这属于共享契约，单独开 `[契约]` PR。评估器接入前，这三类住户的结果是前端样例，界面和报告都标"样例"。

#### 5.10.5 图层

| 图层 | 画什么 | 怎么算 | 什么时候有 |
|---|---|---|---|
| 通行余量 | 地面按住户还剩多少余量着色 | 实时算：自由空间的距离场（EDT）减去当前住户外形的半宽。切换住户立刻重算 | 任何时候 |
| 风险点 | 出过问题的位置，脉冲圆环标记，大小表示次数 | 仿真结束后，把评估器的事件（接触、受阻、够不着、开门失败）和违规（`DOOR_WIDTH`、`TURN_SPACE`、`LIGHT_DARK` 等，见 [simulation](../tech/simulation.md)）按位置累计 | 试住之后 |
| 门扫掠 | 每扇门的开启扇形，和家具或住户重叠的部分标红 | 门的铰链位置、开向和门扇宽度 | 任何时候 |
| 判定外形 | 住户身上半透明的矩形或圆盘 | `personas.yaml` 的外形，说明"判定按这个外形算" | 默认打开 |

通行余量分四档，颜色和图案同时编码：

| 档位 | 余量 | 颜色 | 图案 |
|---|---|---|---|
| 过不去 | < 0 | 朱红 | 交叉斜线 |
| 窄 | 0–5 cm | 琥珀 | 单向斜线 |
| 紧 | 5–10 cm | 柠檬黄 | 圆点 |
| 够 | > 10 cm | 青绿 | 无 |

- 诊断风格下，余量、门扫掠和疏散路线画成地面标线（像停车场和医院地面的引导线），不是悬浮的色块。
- 步入时角落实时显示左右余量，例如"右侧余量 −2 cm"，数字取同一个距离场。
- 通行余量和步入的余量是前端的即时估算，用于看和调；报告里的数字只来自评估器的 run。

#### 5.10.6 改造

改造步骤只给方案卡，现场不拖动家具。修复是多目标搜索：

| 项 | 内容 |
|---|---|
| 目标 | 花费最少；全家通过的任务最多；改动件数最少；余量最大 |
| 约束 | 预算；锁定的家具（"床不要动"）；租房还是自有（租房不改门和墙）；承重墙不动；优先照顾的住户；任何住户都不能比改造前差 |
| 候选改法 | 家具平移、旋转、删除；换成或新增素材库里的商品；门改开向或改推拉门；素材库没有合适的商品时用 Lux3D 生成 |

```text
┌ 改造 ─────────────────────────────────────────────┐
│ 预算 ¥5,000   锁定：主卧床   [租房|自有]            │
│ ┌ 省钱 ───────┐ ┌ 均衡 ───────┐ ┌ 最安全 ─────┐    │
│ │ ¥860  58→79 │ │ ¥2,140 →88  │ │ ¥4,700 →95  │    │
│ │ 2 处改动    │ │ 4 处改动    │ │ 6 处改动    │    │
│ └─────────────┘ └─────────────┘ └─────────────┘    │
│ 花费 × 得分 散点：每个候选一个点，三张卡高亮       │
│ ▸ 试过的改法（24 个）                              │
└───────────────────────────────────────────────────┘
```

- 三张卡是搜索结果里有代表性的三个方案：省钱、均衡、最安全。散点图画出全部候选，横轴花费，纵轴全家得分，前沿上的点连线。点散点里任何一个点都能看那个方案。
- 选中方案后，3D 里家具补间移动到新位置，新商品从卡片飞到原位，旧家具淡出；重跑结束后时间线红叉变绿点，分数滚动到新值。
- 方案里每件商品旁有"换一件"，打开素材库抽屉，只列放得下、适合当前住户的商品，每件标出换上后分数怎么变。
- "试过的改法"列出每个候选改了什么、各任务结果、采纳或淘汰的原因。
- 价格是宜家、西门子中国官网的人民币参考价，标"参考价"；商品清单接入前用样例价格表，标"样例"。

#### 5.10.7 素材库

布局参考宜家线上商城：左边筛选，中间商品卡，右边详情。

- **筛选**：品类、价格区间、适合哪类住户、尺寸上限（宽、深、高）、特性（推拉门、可调高度、扶手等）。
- **商品卡**：主图、名称、参考价。
- **详情**：3D 转台、三维尺寸、来源链接、可动部件（门扇、抽屉）和它们的扫掠范围。
- 目前用 WSR 里的家具。宜家商品清单和 Lux3D 重建的模型接入后替换；`catalog.yaml` 的 S1–S8 换成宜家商品，S9 轮椅和 S10 助行器保留，单独开 PR。

#### 5.10.8 实验室

实验室是试住的批量版，详细界面见 §5.9。四步：数据源 → 设置 → 运行 → 结果。

- **数据源**：链家户型、WSR、户型生成器的输出。实验对象可以是户型库、户型生成器或家具系列。
- **运行**：缩略图网格，每套房一个格子，跑完按结果变色（颜色加图案，同 §5.10.5）。
- **结果**：排行、统计，以及"让全部住户都通过，平均要花多少钱"。
- 点任何一套房，打开试住的体检页；试住里可以把当前户型"加入实验"。

#### 5.10.9 报告

单页 HTML，在新标签页打开，可以直接打印成 PDF 或发链接。

- 顺序：结论（分数、几处过不去）→ 问题（每处一张现场图，实测和要求并列）→ 方案（改了什么、花多少钱、谁变好了、有没有人变差）→ 前后对比图 → 商品清单 → 规范依据 → 假设和样例说明。
- 现场图和对比图用成片档渲染（§5.10.12），右下角带图签。
- 正文用 Pretext 排版，文字绕开插图的轮廓，不是矩形环绕。
- 所有数字来自 run；样例数据和参考价在用到的地方就地标注。

#### 5.10.10 动效与 Pretext

**动效**用 GSAP 做镜头和 3D 物体，面板开合用 CSS transition。

- 全站只有一个编排好的时刻：首页进入工作台时，平面图从地面升起成白模，材质从入户门开始铺满全屋，约 2.5 秒。
- 其他动效都回应用户的操作：
  - 失败时镜头推近到出事位置；
  - 点问题时镜头飞到现场；
  - 应用方案时家具补间到新位置；
  - 分数变化时数字滚动到新值。
- 加载时盲文点位逐个亮起（§5.10.11）。
- 系统设置了"减少动态效果"时，镜头直接切换，平面图不升起，分数直接显示新值。

**Pretext**（`@chenglou/pretext`）用在三处：首页标题和说明、体检讲解、报告正文。

- 做法：每帧把 3D 模型（或插图）的屏幕轮廓投影出来，算出每一行被挡住的区间，再用 `layoutNextLine` 按每行剩下的宽度逐行排版。用户拖动旋转房子看细节时，文字跟着让开，不会挡住模型。
- 文字始终是真实的 DOM 文本，能选中、能被读屏软件读出、能缩放。
- 减少动态效果时，文字固定排在模型旁边，不随旋转重排。

#### 5.10.11 视觉

视觉方向是"图纸与标线"：画面像一张标准户型图升起来的建筑模型，分析结果像医院和停车场的地面引导线一样画在地上。不用手绘、水墨、水彩效果。

**颜色**

| 名称 | 色值 | 用途 |
|---|---|---|
| 清华紫 | `#660874` | 品牌、用户的操作、住户、选中状态。白底上对比度约 11:1 |
| 浅紫 | `#C7A6DE` | 深色背景（夜间、起火、录制）上的品牌色和选中状态。在深墨上约 6.6:1 |
| 暖灰 | `#ECEAE6` | 页面底色、诊断白模的环境色 |
| 深墨 | `#24212A` | 正文、描线、盲文点位 |
| 朱红 | `#D7263D` | 过不去、失败 |
| 琥珀 | `#E8A33D` | 余量窄 |
| 柠檬黄 | `#D9C836` | 余量紧 |
| 青绿 | `#2A9D8F` | 通过 |
| 疏散绿 | `#00A651` | 只用于起火时的疏散箭头 |

- 规则：暖色只表示问题，紫色只表示用户和住户，绿色表示通过和逃生。
- 紫色只用纯色，不做紫色渐变。只借用清华紫这个颜色，不用清华的校徽、校名字体等视觉识别元素。
- 琥珀和柠檬黄只做填充，上面的文字用深墨；所有状态同时带图案（§5.10.5）。

**字体**

| 角色 | 字体 | 许可 |
|---|---|---|
| 中文标题、品牌名"清先住" | 得意黑 Smiley Sans，按用到的字裁剪子集 | OFL |
| 英文品牌名 LiveFirst | 宽体方形无衬线，候选 Michroma | OFL |
| 数字（分数、尺寸、价格） | Barlow Semi Condensed，等宽数字 | OFL |
| 正文 | 系统黑体（Mac 上是苹方） | 系统自带 |

字号按 1.25 倍比例分级；正文行长不超过 40 个汉字。

**盲文**

盲文是贯穿全站的视觉线索，编码按国家通用盲文方案，实现前逐字对照方案原文核对点位。

- 品牌标志：品牌名旁是"先住"两字的盲文点位；首页主图上这几个点用清华紫。
- 加载动画：盲文点位逐个亮起。
- 步骤栏：每一步前面是该步序号的盲文数字（六点格），走过的步骤点位填满。
- 盲文点位是装饰，加 `aria-hidden`；对应的文字另有可读的文本。

**实景和诊断**

| | 实景 | 诊断 |
|---|---|---|
| 用途 | 让家人认出"这是我们家"，视频和首页主图 | 分析问题，报告插图 |
| 材质 | GLB 原有的 PBR 材质 | 白模，墨色描线（深墨） |
| 光照 | HDRI 环境光加日光，柔和阴影 | 均匀环境光，环境光遮蔽加强 |
| 分析图层 | 半透明叠加 | 画成地面标线；风险点是脉冲圆环；门扫掠是扇形；选中物体描紫边 |

**场景**

- **白天**：暖灰天空，日光从窗户进来。
- **夜间**：室内暗下来，只有灯具发光，灯光有光晕。评估器判为照度不足（`LIGHT_DARK`）的路段在地面标出。原型没有夜灯模型，需要新做。
- **起火**：沿用原型 `js/fire-core.js` 的格子仿真（温度、烟、顶棚烟层、火焰、暴露量），只重写画面：地面烟气贴图、顶棚烟层分层下降、火光闪烁、疏散绿箭头沿逃生路线流动。闪烁不超过每秒 3 次。

#### 5.10.12 渲染

两档渲染，按相机是否在动自动切换：

| 档 | 什么时候用 | 做法 |
|---|---|---|
| 实时 | 回放、镜头运动、步入、起火 | three.js 光栅化；postprocessing 合成：N8AO 环境光遮蔽、Bloom、SMAA、AgX 色调映射；Poly Haven HDRI 做环境光；柔和阴影场景加载后算一次；俯视和跟随时把顶棚裁到 1.15 m |
| 成片 | 相机静止约 1 秒后：首页主图、前后对比、报告插图 | MuTracer 路径追踪，逐帧累积，OIDN 降噪，AgX。用 `THREESync` 同步 three.js 场景，不另建一份。可以关掉；失败或设备不支持时留在实时档 |

技术栈（版本已在 npm 上核对过兼容范围）：

| 库 | 版本 | 用途 | 许可 |
|---|---|---|---|
| three | 0.186.0 | 渲染（ES module） | MIT |
| postprocessing | 6.39.5 | 后处理合成（要求 three ≥0.168 <0.187） | Zlib |
| n8ao | 2.0.1 | 环境光遮蔽 | ISC |
| camera-controls | 3.1.2 | 俯视和环绕相机、平滑飞行 | MIT |
| gsap | 3.15.0 | 镜头和物体动效（含全部插件，免费） | GSAP 标准许可 |
| @meimu/mutracer | 0.2.0 | 成片档路径追踪（WebGPU，退到 WebGL2） | MIT |
| @chenglou/pretext | 1.0.0 | 文字绕排 | MIT |
| tweakpane | 4.0.5 | 录制用的隐藏导演面板 | MIT |
| stats.js | 0.17.0 | 帧率，只在 `?debug` 时加载 | MIT |

- 备选：成片档也可以用 three-gpu-pathtracer 0.0.27（只支持 WebGPU，要求 three ≥0.185）。两者选哪个，以 Mac M4 上 Chrome 的实测画质和速度为准。
- 3DGS 重建结果以后用 @sparkjsdev/spark（2.4.0，要求 three ≥0.180）显示。
- 不用 motion.dev、Lenis、lottie：镜头和物体用 GSAP，面板用 CSS 已经够了。
- 第三方库合计约 5 MB，放在 `web/vendor/`，用 importmap 加载，不需要构建步骤。
- 物理单位：升级后灯光按物理单位（坎德拉、勒克斯）设置，原型里的灯光强度要重新调。
- 画面里的暗和烟只是视觉效果；照度不足、烟气暴露、能不能逃出来，都以评估器的结果为准。

#### 5.10.13 录制

视频由用户在本机 Chrome 里边操作边录，台词在对话框里现场打字，所以画面必须实时渲染，不用离线逐帧合成。

- 录制模式（步骤栏的"● 录制"）：隐藏左右面板，只留 3D、字幕、时间线和图签；鼠标指针静止 2 秒后隐藏。
- 导演面板：`?director` 打开 Tweakpane 面板，调镜头位置、焦距、曝光、成片档开关和回放速度，面板不进画面。
- 字幕：住户独白和 Agent 回复以字幕显示在画面下方，深墨底浅色字。
- 视频脚本里用户依次输入：
  1. "我爸坐轮椅，我妈用助行器，下个月搬来这套房"
  2. "我妈晚上经常起夜"
  3. "为什么过不去？"

#### 5.10.14 代码

`web/index.html` 用 importmap 指向 `web/vendor/`，入口模块 `js/main.js` 先 `import * as THREE` 并挂到 `window.THREE`，再按顺序加载其余模块，所以现有模块不用改成 ES module 也能用新版 three。

代码分层（只允许上层调用下层）：

| 层 | 文件 | 职责 | 不做的事 |
|---|---|---|---|
| 引导 | `main`、`app-boot` | 加载库、读 URL 参数、录制预设、键盘、启动 | — |
| 交互 | `nav`、`home`、`panels`、`chat`、`timeline`、`overlay`、`flow`（Pretext 绕排） | 从 store 读状态画 DOM；用户操作一律调用 `S.act(动作, 参数)` | 不直接调用渲染层，不改 store |
| 状态 | `app`、`app-steps` | 唯一的 store `S`（页面、步骤、场景、风格、住户、任务、方案、播放时间、选中物体）；`S.act` 改状态，再通知交互层和渲染层刷新 | 不画 DOM 细节 |
| 渲染 | `viewer`、`fx`（后处理和两档渲染）、`scene-ir`、`avatars`、`resident`、`layers`、`fire`、`night` | 按命令画 3D：`setStyle`、`setScenario`、`setView`、`mark`、`flyTo`、`setPose`、`applyPlan`、`annotate` | 不读 store，不碰 canvas 和标注层以外的 DOM |
| 数据 | `api`、`text`、`assets` | 读 IR、占用栅格、结果并适配；统一文案和单位；按 `assets.json` 找资产 | 不依赖 three.js 和 DOM |

- 接后端时只换 `api`；换 Lux3D 绑骨角色时只换 `avatars`；实验室页复用渲染层、数据层和交互层的详情面板。
- `fire` 调用原型 `fire-core.js` 的格子仿真（它不依赖 three.js），只负责画面。
- GLB 只负责外观。点选、描红、改造预览按节点名找物体：GLB 里有这个节点就改 GLB 的材质和位置，没有就用 IR 白模。IR 白模始终在场景里（不可见），供射线点选。
- 坐标：IR (x, y, z) 对应 three.js (x, z, −y)，与 `export_glb` 一致。原型人物的朝向角 a = yaw + π/2。
- 结果以 B 的仿真结果结构为准，`js/api.js` 做适配；结构冻结前用 `web/tools/make_mock.py` 生成样例，只用于开发界面。

### F1 户型图转 3D（P1 入口；未完成时用数据集户型，比赛计划 E14）

| 项 | 要求 |
|---|---|
| 输入 | 户型图图片（链家式黑白线稿、彩色平面图，或 WSR 自带的 768×768 俯视图）；可选：一个已知尺寸用于定比例 |
| 识别内容 | 墙线、门（位置、宽度、开向）、窗、房间多边形和房间名（OCR 文字 + 布局推断）、比例尺 |
| 输出 | Scene IR 的结构部分（房间、墙、门、窗），每个元素带置信度和 `source: floorplan` |
| 用户确认 | 叠加显示在原图上；门的宽度和开向、房间名可以点改；改过的标 `source: user` |
| 3D 生成 | 墙高默认 2.7 m，门高 2.1 m，窗台 0.9 m；地面按房间类型给材质 |
| 验收（演示） | 演示户型的房间数、门数与原图一致；门宽误差 ≤ 3 cm（与人工标注对比）；演示户型人工复核后才进仿真 |

演示用的户型图：

- 优先用 WSR 自带的俯视图，因为它有真值，可以直接对比"识别出的 3D"和"WSR 原始 3D"，量化识别误差。
- 也可以用链家等平台的户型图，更接近用户手里实际拿到的图。

**另一个入口：导入 3D 模型**（P2，交互原型已实现）。用户已经有 3D 模型时（设计师的方案模型、扫描软件导出的自家房间、WSR 的 `scene*.usdz`），直接导入：

| 项 | 要求 |
|---|---|
| 格式 | OBJ+MTL、STL、3DS、GLB/GLTF、FBX、DAE、USDZ；可同时选配套的材质、贴图和 BIN。压缩的 GLTF（Draco / Meshopt / KTX2）先转成未压缩版 |
| USDZ | 由本机的 OpenUSD 展开引用、实例、旋转和缩放，转成 Y 向上、米制的 GLB 再载入；保留全部可见网格和 USD 自带贴图，吊顶单独隐藏，方便俯视。同一文件按内容缓存，第二次导入直接读缓存。上限 600 万三角面，其他格式上限 180 MB、200 万三角面 |
| 隐私 | 模型在浏览器本机解析；USDZ 交给本机的转换服务（只监听 127.0.0.1），不上传远程 |
| 导入设置 | 单位（米、毫米、厘米、英尺）、向上轴、地面高度都可以改，改完重新导入。STL、3DS 和 USDZ 默认 Z 向上，其余默认 Y 向上 |
| 地面 | 自动取模型底部的大块水平面作地板，只有地板区域可通行；识别不到地板时用模型的平面范围作虚拟地面，并提示用户 |
| 导入后检查 | 显示平面尺寸、地板识别结果和碰撞栅格，提示用户先确认尺度对不对 |
| 能做什么 | 没有门、床、冰箱这些语义，只做自由通行分析：三种身体尺寸（步行、轮椅、助行器）的人群在场景里走向目的地，输出磕碰热点、受阻旅程、到达率、每百米磕碰次数。目的地可以用默认的，也可以在地面点选或输入坐标 |
| 灾害实验 | 选火灾或地震后重新生成人群。火灾按温度、燃料、烟气、风向和墙体阻断更新传播场，人群按危险代价重新规划出口；地震按确定性地震动累计结构损伤，触发倒塌，碎片按刚体掉落并和人群碰撞。可调强度和 1× / 2× / 4× 倍速，住户头顶的状态气泡显示警觉、避烟、改道、受困、已安全 |
| 边界 | 人群是随机的，热力按本次最大值归一化，结果只用来看"哪里容易磕碰"，不进体检分数。火灾和地震是确定性的降阶模型，火焰、烟气、碎片是视觉表达，不等于 CFD、结构动力学或消防评估，也不进体检分数。要做任务体检，先把模型转成 Scene IR（补门、家具语义） |

这个入口同样适用于办公室、展馆等公共空间（是否放进作品见比赛计划 §10 #3）。WSR 住宅能直接以 USDZ 导入，实验室模式里的任一 WSR 住宅都可以在浏览器里打开原始模型对照。

**商品到场景**（技术细节见 [aholo-lux3d §3](../tech/aholo-lux3d.md)）：

| 步 | 做什么 | 界面上看到什么 |
|---|---|---|
| 1 | 从商品页取主图和标称尺寸 W×D×H，写进商品库 | 商品卡：品牌、型号、尺寸、价格、来源链接 |
| 2 | Lux3D 按主图补成四视图后生成 3D 模型；没有可用的图时按文字描述生成，模型只代表品类外形；冰箱再做关节化，得到门的开启扫掠 | 商品卡状态"生成中" |
| 3 | 按标称尺寸缩放，原点落地、Z 向上；三个轴的缩放比差异超过 15% 判为不合格，换图重试 | 状态"尺寸已校准"或"QA 未过" |

| 5 | 合格的模型入库；同一件商品 QA 失败两次就用包围盒加主图贴片 | 商品卡能看三版对比：首次生成、尺寸校准后、入库 |
| 6 | 修复（F5）选中这件商品时，替换场景里对应的物体，按商品库尺寸（含模型量取值）更新 IR | 商品飞入动画（§5.7 链路 2） |
| 7 | 对所有住户重新仿真 | 时间线和分数变化 |

商品来源覆盖多个品牌：`src/ha/assets/catalog.yaml` 的 S1–S10 包括家电、卫浴、门、家具和辅具，每件带商品页链接、标称尺寸和 `source_quality`。三版对比同时是报告书里"Lux3D 资产迭代"那一页的素材（比赛计划 §4）。

### F3 家具布置与整屋重新布局

两种模式：

- **按现有布置**：用户上传的是带家具的户型（或 WSR 户型），直接进仿真。
- **帮我布置 / 整屋重新布局**：布局 Agent 按房间功能从家具库选款并摆放，参考 SAGE 的流程：
  1. 按房间类型列出必需家具（卧室要有床和床头柜，卫生间要有马桶和洗手盆，厨房要有冰箱和灶台）和可选家具。
  2. 逐件摆放，满足几何约束：不穿墙、不重叠、靠墙的靠墙、不挡门窗、不压门扫掠。
  3. 视觉检查（俯视图加角度渲染）和规则检查（通道宽度、交互区）。
  4. **无障碍约束作为布局目标的一部分**：每个候选布局都交给评估器跑住户任务，分数参与选择。

整屋重新布局和普通 AI 布局的区别在于第 4 步：普通布局只看"摆得下、好看"，清先住要求"这个人用得了"。

| 项 | 要求 |
|---|---|
| 输入 | 结构 IR、住户、预算、用户约束（"沙发不动""不买新床"） |
| 输出 | 1–3 个布局候选，每个带商品清单、总价、评估分数 |
| 验收（演示） | 演示户型上，重新布局后轮椅住户的 P0 任务全部成功，步行对照不变差 |

### F4 数字住户试住：仿真与碰撞事件

| 项 | 要求 |
|---|---|
| 住户 | 6 个画像，加步行对照和担架，参数见 `src/ha/resident/personas.yaml` |
| 任务 | T1–T8，适用关系见 personas.yaml 的 `tasks`；任务定义见 [simulation §7.1](../tech/simulation.md) |
| 判定 | L0 圆盘预筛 → L1 SE(2) 路径（真实外形和转向约束）→ L2 局部检查（转身、停留、够取、转移）→ L3 物理回放（只用于镜头和临界样本） |
| 开门 | 逐项检查：开门站位能否到达、拉门时把手侧余量够不够、开门力是否在画像上限内、门扇扫掠是否碰到住户或家具。哪一项不过就报哪一项 |
| 探测（视障住户） | 沿住户的已知路线，检查白杖探不到的突出物：离地 0.685–2.03 m 之间、伸进通行路径超过 0.10 m 的物体（ADA 307.2；GB 对应条文在 [standards-check](../standards/standards-check.md) 核对），包括吊柜下沿、开着的柜门、墙上凸出物。路线上临时放的东西按 T8 处理 |
| 碰撞事件 | 找不到无碰撞路径时用软碰撞搜索，给出撞在哪里、撞了哪个物体、撞了多深 |
| 事件流 | 每个事件带时间、位置、物体 id、类型、实测值、要求值、规范条文，前端按时间线播放 |
| 独白 | 决策层 LLM 只从运动层给出的候选动作里选，独白数字要和事件对得上 |

事件类型（前端图标和颜色按这个分）：

| 事件 | 例子 | 颜色 |
|---|---|---|
| COLLISION | 轮椅左扶手擦到门框，穿透 4 cm | 红 |
| BLOCKED | 走廊被鞋柜挡住，最窄 0.71 m | 红 |
| TURN_FAIL | 卫生间里转不了身，需要 1.50 m 圆，只有 1.12 m | 红 |
| REACH_FAIL | 开关 1.30 m，坐姿够不到（上限 1.22 m） | 红 |
| LOW_MARGIN | 过门余量只有 3 cm，能过但很勉强 | 黄 |
| DOOR_SWING | 冰箱门开启扇形碰到轮椅脚踏 | 黄或红 |
| PROTRUSION | 吊柜下沿离地 1.45 m，伸进走道 0.32 m，白杖探不到 | 红 |
| DARK_SEGMENT | 起夜路径上一段只有中位照度的 22% | 黄 |
| HINT | 卫生间瓷砖湿滑提示（不计分） | 灰 |

### F5 优化建议与修复

| 模式 | 做法 | 适用 |
|---|---|---|
| 小改 | 按代价搜索编辑：平移、旋转（1）→ 删除非必需物体（2）→ 换同类商品、加扶手、换易握门执手（3）→ 门改开向或改推拉（4）→ 门加宽（6）。最多组合 3 个编辑 | 已入住或预算少 |
| 整屋重新布局 | 走 F3 的布局流程，把评估分数作为目标 | 装修前、新房 |
| 用户追问 | "如果……呢"转成一次编辑，单独评估 | 任何时候 |

每条建议写成"改什么 → 为什么 → 改完怎样"三段，例如：

> 把床向左挪 55 cm → 床右侧只有 65 cm，轮椅贴不过去 → 挪完右侧 1.20 m，你爸可以自己从轮椅转到床上（T4 失败 → 成功）。

修复过程对用户可见。修复 Agent 每试一个候选，都完整重跑一次仿真；界面上的"试过的改法"（§5.4）列出全部候选、各自的重跑结果和采纳或淘汰的原因。只有让分数变好、且没有让任何住户变差的候选才会进方案。试完仍修不好的任务照样显示失败，并写明试过什么。这需要修复 Agent 在结果里输出候选记录（simulation §9.2）。

### F6 仿真即评估器：验证优化

- 任何方案（小改、重新布局、用户手动拖动）都必须重新跑仿真，结果才算数。LLM 提出的方案只是候选。
- **所有住户都要重跑**。修好轮椅的问题，不能让助行器使用者或步行对照变差；变差的方案直接淘汰或标红提醒。
- 评分规则冻结后不改：适用任务成功率 × 100，红色违规每条扣 5、黄色扣 2，截断到 0–100（[simulation §8.2](../tech/simulation.md)）。
- 同一输入重跑结果一致：运动层确定，LLM 调用用 temperature 0 加缓存。
- 前后对比固定住户、任务、起点和栅格精度，给出：分数变化；每个任务成功与否的变化；碰撞尝试、路径失败、转向失败、够取失败、开门失败、转移失败各几次；最小余量变化；任务耗时；花费。耗时只比较前后都成功的任务，没有共同成功的任务时写"不适用"。
- 完成率提高不代表每条路径的余量都变大，最小余量按实际走过的路径、住户外形和门扇单独计算。

### F7 报告与商品清单

报告格式示例（户型编号和数字都是占位）：

```text
户型 scene000123 · 三室一厅 · 92 m²         住户：手动轮椅使用者
总分 54 / 100          5 个任务中有 2 个能完成

[红] 卧室到卫生间：失败
     卫生间门净宽 0.72 m，要求 ≥ 0.80 m        原因物体：door_bathroom1
     卫生间内无 1.50 m 转身圆                  原因物体：washbasin_02、cabinet_07
[红] 取用冰箱：失败
     冰箱前方停留空间被餐椅占用                 原因物体：chair_03
[黄] 入户到沙发：完成，但最窄处只有 0.86 m（通道要求 0.915 m）  原因物体：shoe_cabinet_01
[绿] 上床、床椅转移：完成

修复建议（按代价从低到高）
  1. 餐椅 chair_03 移到餐桌另一侧             代价 1    取物：失败 → 成功
  2. 洗手台换成悬挑款（台下净空 0.68 m）        代价 3    卫生间内可以转身
  3. 卫生间门改成推拉门                       代价 4    如厕：失败 → 成功
修复后：总分 54 → 88，5 个任务全部完成
```

报告里所有数字都由评估器计算，大模型只负责把结果写成通顺的话，不改数字。在上面的结构之外，报告还要有：

- 户型识别来源和用户修正记录（哪些尺寸是用户改过的）。
- 家具来源：商品页链接、抓取时间、尺寸是标称还是估计。
- 方案对比表：方案 A / B / C 的花费、分数、各住户任务结果。
- 规范依据：每条违规列出 GB 55019 / GB 50763 条文，ADA 作对照列。

### F8 实验室模式：批量体检与家具系列评测（B 端）

- 场景：一次处理多套住宅。来源有三种：按户型分布批量生成（生成平面 → 转三维 → 摆家具，§2.3）；数据集（WSR 500 套，SAGE-10k 单房间作补充）；上传户型库（走 F1 识别）。
- 运行：只用规则策略，不调 LLM，结果确定。实验配置（场景清单、画像、任务、变量、种子）随结果一起保存。
- 批量体检输出：达标率分布、失败原因排行、按房间类型的问题分布、最差户型列表。
- 家具系列评测输出：同一批住宅、同一批住户下，基线商品和待测系列的成对对比，按画像、任务、户型拆开，列出变好、变差、不变的住宅数和最差案例。家具厂只需给商品图和参数表：外包尺寸来自参数表，外形和细节尺寸由 Lux3D 批量建模和量取（§2.4）。
- 设计变量扫描：只改一个住宅设计变量，画出各画像成功率随它变化的曲线。评估器的阈值和评分规则不随实验改变。
- 界面见 §5.9。批量体检是规模化镜头的素材，也是面向开发商、设计院、家具厂和科研用户的功能原型。

## 7. 视频 demo（约 3 分钟）

视频按 §4 的产品流程走，**每个镜头都是产品真实界面的录屏**，不做和产品脱节的动画。录屏失败时用俯视 mp4 兜底（[simulation §10](../tech/simulation.md)）。

分镜见[比赛计划 §9](../../plans/hackathon-plan.md)，每个镜头对应的实验和优先级也在那里。

拍摄要点：

- 演示户型按比赛计划 §10 #2 决定；选定后人工复核识别结果和门宽。
- 每个数字镜头都要在画面里能看到来源（实测值、要求值、条文号）。
- 第一人称眼高 1.2 m（坐姿），步行对照 1.6 m，让观众感受视角差别。
- 字幕里的数字和报告完全一致，录制前用同一份运行结果生成。
- 按 §11 降级的功能，按比赛计划 §9 的规则处理：对应实验没过门的镜头去掉，修不好的项放进片尾"下一步"。

表现力设计：

- **第一人称视角**：坐姿眼高约 1.2 m，让观众“坐上轮椅”去看门框和台面。
- **内心独白字幕**：“门有点窄，我把脚踏收一下……还是蹭到门框了。”独白由决策层生成，内容和运动层的真实结果一致。
- **圆盘与轮椅对比**：同一扇门，圆盘模型显示能通过，矩形轮椅显示过不去。用这个镜头说明为什么要按真实外形仿真。
- **颜色语言**：红色表示失败或碰撞，黄色表示余量不足，绿色表示通过。热力图显示住户在哪里停顿、哪里发生擦碰。
- **改造前后分屏**：左边是原户型和失败轨迹，右边是修复后的成功轨迹，下方的指标数字滚动变化。
- **商品落位动画**：Lux3D 生成的新商品从商品卡飞进场景，替换掉原有的家具；飞入前先闪过三版对比（首次生成、尺寸校准后、入库）。
- **绑骨住户**：人体、轮椅、助行器、白杖都是 Lux3D 生成的模型，住户坐着轮椅前进、推着助行器慢走、陪护推着轮椅过门、白杖左右扫动、伸手够冰箱，动作和轨迹同步（§5.6 住户角色和动作）。够取镜头最直观：手伸到够取上限停住，和冰箱冷藏层之间标出差多少厘米。
- **自己走一遍**：路演时现场操控轮椅撞上门框，再切到改造方案走过去（§5.7 链路 5）。
- **精细画质**：录屏一律开精细档（§5.6）。
- **夜间和烟气场景**：关灯后画面只剩照度图；烟气从厨房蔓延时，给出不同住户的疏散时间对比。
- **担架镜头**：俯视图里一副担架在卧室门口反复尝试转弯，最后标红“抬不出去”。改造后同一路径变绿。
- **杂物容错**：门口逐个放快递箱，余量条从绿变黄再变红，显示“这套房离走不通还差多少”。

### 9.4 进入顺序

1. 先做设计师工作台：用户专业，愿意为"有依据的报告"付费，也能帮我们标注和校准评估器。
2. 再接平台 API：和家居平台合作，把"换上之后的效果证明"放进商品推荐。
3. C 端随平台流量上线，不单独投放获客。
4. 实验室模式按项目接开发商的批量体检和家具厂的系列评测，积累户型数据；同时向科研机构开放。

## 10. 边界声明

视频和报告里都要写：

- **不替代专业评估**。清先住给出的是基于规范和仿真的风险提示，改造前建议请专业人员上门复核。
- **规范依据**：阈值以 GB 55019-2021（强制）为主、GB 50763-2012 补充，ADA 2010 作为对照列（[standards-check.md](../standards/standards-check.md)）。
- **尺寸来源**：报告写明哪些尺寸来自户型识别、哪些经用户确认、哪些由 Lux3D 模型量取（标“由模型量取，商品页未标注”）、哪些来自类目模板（质量、门开启力、开关高度标为“假设”）。门宽等关键尺寸建议现场实测。
- **商品数据**：价格和尺寸以抓取时间为准，报告里写明抓取日期和来源链接。
- **示意分析**：夜间照明是相对照度，烟气疏散是简化扩散模型，担架按平抬计算，导入 3D 模型里的火灾和地震是确定性降阶模型。它们用来比较不同住户之间、以及改造前后的差别，不代表消防、抗震或照明认证。
- **实验室模式的统计**：结论只对所用的场景集成立。数据集和生成住宅的户型分布不等于真实住房存量，报告里写明场景来源、数量和筛选条件。
- **LLM 的作用**：负责理解需求、选动作、写独白和建议文字。分数、尺寸、成败判定都来自确定性的运动层和评估器。
- **几何判定**：够取、开门、床椅转移按外形、扫掠和够取范围判定，不含人体动力学、抓握力学和照护能力评估。

## 11. 降级方案

主线（仿真 → 体检 → 修复 → 验证）优先。户型识别、整屋布局、商品抓取按下表逐级降级，降级后在视频和报告里标注。

| 范围 | 完整目标 | 降级 1 | 降级 2（保底） |
|---|---|---|---|
| 户型图转 3D | 任意户型图（线稿、彩图）自动识别墙、门、窗、房间，生成 3D | 只支持 WSR 俯视图：用 WSR 真值校准识别算法，识别失败的元素由用户在界面上点选修正 | 识别步骤做成"半自动"：界面上展示识别流程，结构 IR 实际取自 WSR 导入（M1），视频用数据集户型做入口（比赛计划 §9 镜头 3） |
| 整屋重新布局 | 布局 Agent 按房间功能选款、摆放，评估分数参与选择，输出 1–3 个候选 | 只重新布局 1–2 个房间（主卧、卫生间），其他房间保持原样 | 退回小改（simulation §9 的按代价编辑搜索），视频只展示小改 |
| 爬虫抓取家具参数 | 多站点、6 个品类、每类 20–50 款 | 单站点、2–3 个品类（冰箱、床、柜子），≥ 50 条 | 只用 `src/ha/assets/catalog.yaml` 里人工核对的 10 个 SKU（S1–S10） |

其他风险：

| 风险 | 影响 | 降级办法 |
|---|---|---|
| 评估器（L0–L2）没按时完成 | 主线断掉 | 优先级最高；L1 太慢时降 θ 档位或放粗栅格 |
| LLM 不可用 | 意图解析、独白、布局建议 | 意图解析用关键词规则 + 按钮；独白用模板句；布局用规则 |
| Lux3D 生成质量不过 QA 门 | 商品飞入镜头 | 包围盒加主图贴片 |
| 模型量取误差超过验证门 | 台下净空、把手高度等细节判定 | 该量取项退回类目模板值并标“基于模板假设”，模型只用于画面 |
| Lux3D 绑骨或动作重定向效果不好 | 住户观感 | 用原型 `js/avatars.js` 的程序化人物、轮椅和助行器；再不行用方盒和圆柱，外形叠加层照常显示 |
| 自由步入帧率不够 | Demo 链接体验 | 降栅格分辨率、关精细画质；仍不够时改成点选目的地、住户自动走过去 |
