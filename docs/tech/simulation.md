## 2. 数据流

```text
WSR usdz + metadata.json          户型图识别得到的结构 IR（agent-backend §7）
  │ M1 导入                            │
  ▼                                    ▼
Scene IR（JSON）+ 分层占用栅格（npz）+ 展示用 GLB
  │ M2 属性补全（模板）        M3 Lux3D 资产库（补缺、替换）
  ▼                             │
补全后的 IR ◄───────────────────┘
  │
  │  M4 住户画像卡 + M5 任务
  ▼
┌──────────── 数字住户 ────────────┐
│ 决策层 LLM：选动作、应变、独白     │
│        ↕ 动作请求 / 执行结果       │
│ 运动层：SE(2) 规划、开门、够取      │
└───────────────┬─────────────────┘
                ▼
M6 评估器：L0–L2 判定，L3 MuJoCo 回放，照明，烟气
                │ 违规报告（按物体归因）+ 指标
                ▼
M7 修复：按代价搜索编辑 → 重新跑 M5/M6 → 改造前后对比
                │
                ▼
M8 可视化：3D 网页、体检报告、视频素材        M9 500 套统计；方案演化（可选，§9.3）
```

层和层之间只交换文件：IR、轨迹、违规报告。每次运行写到 `$HA_OUTPUTS/runs/<实验>/<run_id>/`，带 `manifest.json`（输入哈希、代码 commit、参数、模型名）。

## 3. M1 场景导入（WSR → Scene IR）

输入：`raw/full/scene/sceneNNNNNN/{.usdz,_metadata.json,.png}`。

| 步骤 | 做法 | 依据（WSR 数据） |
|---|---|---|
| 房间 | USD 默认 prim `/root` 下的 `ground/ground_<room>_<材质>_<id>` 网格投影到 XY，合并成多边形；材质名映射为地面类型（瓷砖、木地板） | 500 套都有按房间拆分的地面网格，共 4,424 个房间 |
| 房间类型 | 名字前缀：livingRoom、bathroom、kitchen、masterBedroom、eldersRoom、entranceHall 等 | metadata 和 prim 名一致 |
| 墙 | `/root/wall` 网格，按高度带切片得到墙体多边形 | 墙带 CollisionAPI |
| 门 | `/root/door` 下的门；铰链关节 → 平开，取转轴位置和角度范围算开向和扫掠扇形；滑轨关节 → 推拉；没有门扇 → 门洞 | 门 3,687 扇，按导入器分类：平开 3,009、推拉 657、门洞 21 |
| 门净宽 | 用门扇网格的宽度，减去开启后门扇厚度和挡块；外框包围盒只作参考 | 外框包围盒宽度 10% 分位 0.82 m，含门框 |
| 家具 | metadata 的 `world_aabb`、`transform`、类目；需要精确外形时用网格按高度带切片 | metadata 共 31,711 个 product：门 3,687、窗 5,730，其余 22,294 个是物体；8 个物体没有包围盒 |
| 灯 | RectLight、SphereLight 的位置、尺寸、强度 | 过滤异常值后每套 17–407 个灯，中位 262 |
| 缺失引用 | 子 USD 打不开时，按 metadata 包围盒补，并记入报告 | scene000000 缺 1 个（柜内的锅） |

**分层占用栅格**：分辨率 0.05 m。每个物体按高度带切片，得到它在每一层的占用：

| 层 | 高度 | 用途 |
|---|---|---|
| floor | 0–0.05 m | 门槛、地面高差 |
| toe | 0.05–0.30 m | 轮椅脚踏可以伸进桌下、台下 |
| body | 0.30–1.40 m | 轮椅扶手和人身体 |
| head | 1.40–2.00 m | 吊柜、站立的人 |

每个格子同时记录占用它的物体 id，用于违规归因。

**展示用 GLB**（`src/ha/ir/export_glb.py`）：网页查看器用 three.js，直接加载 glTF/GLB；WSR 的 USDZ 是二进制 USDC，贴图很重，浏览器读不了。GLB 只用于展示，不参与打分。

- 每个 IR 物体和门导出为一个 glTF 节点，节点名就是 IR 的 `id`，网页按违规报告里的 `object_id` 高亮对应节点。墙、地面、窗各自一个节点，不属于任何 IR 实体的网格归到 `other:<顶层 prim>`。
- 颜色：取绑定贴图的平均色（UsdPreviewSurface 的 `diffuseColor` 或 OmniPBR 的 `diffuse_texture`）；没有贴图时用常量颜色；都没有时按类别（墙、地面、门、物体等）给固定颜色。
- 网格按顶点聚类减面（默认 0.01 m 网格）。
- 输出 glTF 的 Y 向上（Scene IR 是 Z 向上），同目录写一份 `<scene>.nodes.json` 列出所有节点。

### 3.1 Scene IR（`ha.scene_ir` v0.1）

字段以 [src/ha/ir/schema.py](../../src/ha/ir/schema.py) 的文档字符串为准，改动属于共享契约（见 [CONTRIBUTING 共享文件](../../CONTRIBUTING.md#共享文件)）。单位米，Z 向上，坐标系与源 USD 一致。每套户型一个 JSON 加一个分层占用 npz。

| 键 | 主要字段 |
|---|---|
| `schema`、`version`、`scene_id`、`source`、`bounds` | 格式标识、源文件信息、场景 XY 范围 |
| `rooms[]` | `id`、`type`、`floor_material`、`floor_kind`、`floor_z`、`area`、`polygons[]` |
| `walls` | body 层墙体掩码的轮廓多边形 |
| `doors[]` | `id`、`rooms[]`、`kind`（平开、推拉、门洞）、`opening_width`、`clear_width`、`leaves[]`（见 `ha.ir.doors`） |
| `objects[]` | `id`、`category`、`type`、`room`、`prim_path`、`aabb`、`world_matrix`、`mass_kg`、`has_collision`、`joints[]`、`footprint`、`z_range`、`layer_cells{toe, body, head}`、`geometry_source`（mesh 或 aabb_fallback）、`label` |
| `lights[]` | 通过异常值过滤的灯；其余放 `lights_excluded[]` |
| `windows[]` | `id`、`rooms[]`、`aabb` |
| `occupancy` | npz 文件名、栅格参数、各层高度区间、物体标签数 |
| `report` | `missing_refs[]`、`warnings[]`、计数、耗时 |

M2 补全后再加三类字段：`under_clearance`（台下、桌下净空，轮椅脚踏可以伸进去）、柜门和抽屉的扫掠多边形、`interaction_zones`（床侧转移区、马桶侧方空间、柜前停留区，带够取高度区间）。补出的值都标 `source: template`。尺寸取用顺序：商品页写了的用标称尺寸（`source: catalog`）；没写的用 M3 从 Lux3D 网格量取、通过验证门的值（`source: lux3d`）；都没有时用模板（`source: template`）。

## 4. M2 属性补全

模板放 `src/ha/enrich/templates.yaml`，每个补出的值都标 `source: template`。

| 属性 | 规则 |
|---|---|
| 质量 | 类目密度 × 包围盒体积 × 填充率；只补 metadata 缺失的项 |
| 交互区 | 床：长边 1.20 m 宽的通道（GB 55019 3.4.6；至少一侧判定，另一侧只报告）；马桶：从侧墙 1.525 m × 从后墙 1.42 m 的净空（ADA 604.3.1）；冰箱和柜子：正前方 0.76 × 1.22 m 停留区（ADA 305.3）；沙发：正前方 0.90 m（自定） |
| 够取目标 | 冰箱：冷藏层 0.4–1.5 m；吊柜：下沿高度取自网格；开关：优先用 WSR 里的 `switch` 物体高度，没有时按门把手侧墙上 1.30 m（国内常见安装高度，标为"现状假设"），合规线是 0.85–1.10 m（GB 55019 3.1.6） |
| 门的开启 | 平开门开启力默认 30 N，推拉门 20 N（自定假设，没有实测来源）；门把手默认执手式 |
| 地面防滑 | 卫生间和厨房的瓷砖标"湿滑风险"，只做提示，不计分 |

模板补出的值进入判定时，违规记录带 `source: template`，报告里标"基于模板假设"，与实测或数据集原值的结论分开列。例如平开门默认 30 N 高于上肢受限画像的 22.2 N（ADA 404.2.9）和 25 N（GB 55019 2.5.4），没有实测开启力的平开门对这个画像都会报违规，这些违规都标"基于模板假设"。

## 5. M3 Lux3D 资产工厂

生成路线和接口细节见 [aholo-lux3d.md](aholo-lux3d.md) §3，积分价格也在那里。仿真这边只关心进入 IR 之前的三件事：

- 规范化：Z 轴朝上、原点落地，按 `src/ha/assets/catalog.yaml` 的标称尺寸缩放。QA 门：三个轴的缩放比之间差异超过 15% 就判为不合格。
- 冰箱、柜子的铰接结果给出门扫过的范围；CoACD 凸分解给 MuJoCo 用。
- 细节尺寸量取：在规范化后的网格上量台下净空、把手和操作面板高度、离地高度、桌腿间距，铰接结果给出门扇扫掠。验证门：商品页或规格书写了该项的 SKU 上误差 ≤ 2 cm（自定），每项至少核对 2 件（比赛计划 E18）。通过的写进 IR，标 `source: lux3d`；没通过的项退回模板值。
- 每次 create 都追加到 `$HA_OUTPUTS/assets/<run_id>/ledger.jsonl`，失败的也记。

外包尺寸以商品页为准。违规记录里 `source: lux3d` 的尺寸，报告标“由模型量取，商品页未标注”，和商品页尺寸的结论分开列。

## 6. M4 住户画像卡

画像卡放 `src/ha/resident/personas.yaml`。决策层和运动层读同一份。标“自定”的数值没有规范出处，是我们设定的。

| 参数 | 手动轮椅 | 助行器使用者 | 上肢受限 | 步行对照 |
|---|---|---|---|---|
| 外形 | 矩形 0.70 × 1.20 m；脚踏在前部 0.30 m，只占 toe 层 | 矩形 0.65 × 0.80 m | 圆盘 r=0.25 m | 圆盘 r=0.25 m |
| 运动 | 非完整约束；可原地转，但转身扫过的圆要放得下 | 近似完整约束，转弯每侧需额外 0.10 m 余量 | 完整约束 | 完整约束 |
| 速度 | 0.8 m/s；余量小于 0.10 m 时降到 0.4 m/s | 0.5 m/s | 1.0 m/s | 1.15 m/s |
| 转向速度 | 60°/s | 30°/s | 90°/s | 120°/s |
| 够取高度 | 0.38–1.22 m（ADA 308 坐姿；有障碍时正向 1.12 m、侧向 1.17 m） | 0.60–1.50 m（弯腰受限，自定） | 0.70–1.40 m（抬手、弯腰都受限，自定） | 0.40–1.80 m（自定） |
| 水平够取距离 | 正面 0.50 m，侧面 0.25 m | 0.45 m | 0.40 m | 0.60 m |
| 开门 | 推门可以；拉门要求把手侧有 ≥ 0.455 m 余量、垂直深度 1.525 m（ADA 404.2.4.1；GB 墙垛 0.40 m 一起报告） | 开门时要松开助行器，耗时加 6 s | 可用的力 ≤ 22.2 N（ADA 404.2.9），GB 25 N 并列；不能拧圆球把手 | 无限制 |
| 门槛 | ≤ 0.015 m 且斜面 ≤ 1:10（GB 55019 2.5.3）；ADA 13 mm 并列 | 同左 | 无限制 | 无限制 |
| 夜间照度需求 | 路径上相对照度 ≥ 0.30（以全部开灯时户内中位值为 1，自定） | 相对照度 ≥ 0.50（易跌倒，要求更高，自定） | 同轮椅 | 不检查 |

**担架（T7 专用的运送体，与住户画像分开）**：担架本体是 0.60 × 1.90 m 的矩形，前后各有一名救护人员，用 r=0.25 m 的圆表示。三者组合成一个刚体，只占 body 层。允许原地转和倒车，速度 0.6 m/s。结论标注"按平抬担架计算"。实际救护时可以竖起担架或改用楼梯椅，所以抬不出去表示存在风险，结论按风险报告。

地面湿滑只做提示：卫生间和厨房的瓷砖地面在报告里标 SLIP_HINT，不计分，也不进评估。

起点、终点由交互区和门的位置自动生成。生成不出来（例如户型没有冰箱）就记为"任务不适用"，不算失败。

### 7.2 动作原语（运动层）

| 原语 | 输入 | 输出 |
|---|---|---|
| `navigate` | 目标位姿 | 路径、耗时、最小余量和对应物体、碰撞事件 |
| `open_door` | 门 id，推 / 拉 / 滑 | 是否能开、需要的站位、门扇扫掠是否碰到住户、耗时 |
| `pass_door` | 门 id | 净宽余量、门槛 |
| `turn_to` | 朝向 | 是否能原地转；不能时需要几次倒车调整 |
| `approach` | 交互区 id，正面 / 侧面 | 停留空间是否被占、被谁占 |
| `reach` | 目标 id | 高度和水平距离是否在画像范围内 |
| `transfer` | 转移区 id | 转移区是否够大、是否被占 |
| `request_help` / `give_up` | 原因 | 结束任务，记为失败并写明原因 |

每个原语都返回统一结构：`{ok, duration_s, events[], min_clearance, blocking_object_id, fail_code}`。

### 7.3 决策层与运动层的接口

1. 运动层先根据当前状态列出**候选动作**，每个带上预计结果。例如"走主卧门：余量 −0.08 m，会碰到门框"或"绕走廊：多 6 m，余量 0.12 m"。
2. 决策层（LLM）只能从候选动作里选，并输出 `{choice, reason, monologue}`。它不能编造候选之外的动作或数字。
3. 运动层执行选中的动作，把真实结果交回决策层，进入下一步。每个任务最多 20 步。
4. 独白必须引用运动层给出的数字。生成后由程序检查：独白里的数字和事件对不上就重新生成，最多 2 次，仍不一致就改用模板句。
5. 调用参数固定：temperature 0，缓存键是 JSON 数组 `[模型名, system, prompt]` 的 sha256。重跑时直接读缓存，保证可复现。
6. 另有一个**规则策略**，接口与 LLM 相同（总是选成功率最高、代价最低的候选）。LLM 不可用时用它，演示不会因此中断。打分时两种策略都跑，报告里分开记录。

## 8. M6 评估器

### 8.1 判定层级

| 层 | 做法 | 输出 |
|---|---|---|
| L0 圆盘预筛 | body 层欧氏距离变换，按住户外接圆半径做连通分量。圆盘都过不去的，矩形一定也过不去 | 快速判"不可达"，并给出卡住的位置 |
| L1 SE(2) 路径 | (x, y, θ) 上做 Hybrid-A*：0.05 m 栅格，θ 分 24 档（15°）；运动基元包括前进、后退、圆弧，轮椅另有原地转。每个朝向的外形核预先算好，对 toe 层和 body 层分别膨胀（cv2），得到 24 张构型空间障碍图 | 路径、耗时、最小余量及对应物体 |
| L1 软碰撞 | 找不到无碰撞路径时，允许穿透但按穿透深度加代价，再搜一次 | 碰撞事件：位置、物体 id、穿透深度。用来回答"撞在哪里" |
| L2 局部检查 | 在目标点检查转身空间（1.50 m 圆或 T 形）、停留空间（0.76 × 1.22 m）、够取、转移区 | 违规列表 |
| L3 物理回放 | 只针对视频镜头和余量小于 0.05 m 的样本，在 MuJoCo 里沿 L1 路径回放（见 §8.5） | 接触点、接触力、穿透深度 |

门的处理：关着的门是障碍。`open_door` 检查住户站位和门扇扫掠扇形是否冲突。通过时，开到 90° 的门扇作为障碍参与 `pass_door`。

### 8.2 指标

每个（户型，住户，任务）一条记录：

| 字段 | 含义 |
|---|---|
| `success`、`fail_stage`、`fail_code` | 是否完成；在 L0–L2 哪层失败；失败编码 |
| `collisions`、`max_penetration_m` | 软碰撞事件数和最大穿透深度 |
| `min_clearance_m`、`min_clearance_object` | 全程最小余量和对应物体 |
| `turn_failures`、`k_point_turns` | 原地转不了的次数；需要几次倒车调整 |
| `reach_failures` | 够不着的目标数 |
| `time_s`、`path_m` | 任务耗时（移动加动作）和路径长度 |
| `violations[]` | `{code, object_id, measured, required, standard, location, source}`；`source` 为 `template` 时报告标"基于模板假设" |
| `l3_contacts` | 只在做过 L3 回放的记录里出现：接触对、接触力、穿透深度。L3 不改变 `success` 和分数 |

违规编码：DOOR_WIDTH、DOOR_SWING_BLOCK、DOOR_PULL_CLEARANCE、THRESHOLD、CORRIDOR_WIDTH、TURN_SPACE、PARK_SPACE、TRANSFER_ZONE、REACH_HEIGHT、REACH_DIST、LIGHT_DARK、SWITCH_HEIGHT、SWITCH_REACH、EVAC_MARGIN、STRETCHER_BLOCK、CLUTTER_MARGIN。提示类（不计分）：SLIP_HINT。

户型总分（冻结后不改）：按适用任务等权计算成功率 × 100，每条红色违规扣 5 分、黄色扣 2 分，结果截断在 0–100。红色指导致任务失败的违规，黄色指任务完成但余量低于规范的违规。

### 8.3 夜间照明（示意）

- 地面 0.05 m 高度处建 0.10 m 栅格。每个灯对每个格子的贡献按"强度 × 面积 × 余弦 / 距离²"估算；墙体遮挡用 body 层射线检测。
- USD 里的灯光强度没有标定成勒克斯，所以只报**相对照度**：以"全部开灯"时户内的中位值为 1。
- 夜间配置：只开起点卧室、走廊、卫生间的灯。T6 输出路径上最暗一段的相对照度、长度和位置。
- 开关高度优先取 WSR 的 `switch` 物体；没有时用 M2 模板（门把手侧 1.30 m）并标为"基于模板假设"。高于 GB 55019 3.1.6 的 1.10 m 报 SWITCH_HEIGHT；高于住户够取上限（轮椅 1.22 m）报 SWITCH_REACH。

### 8.4 烟气疏散（示意）

- 0.10 m 平面栅格上的显式扩散模型。火源放在厨房灶台或油烟机处，没有的话放厨房中心。墙不透；门开着时传导系数为 1，关着时为 0.05。
- 时间步长满足 D·Δt/Δx² ≤ 0.2，保证数值稳定。
- 浓度超过临界值的时刻记为该格子的"不可用时间"。T5 中，住户沿路径行进时到达的每个格子都必须还没到不可用时间。
- 所需疏散时间 = 反应时间 60 s（假设）+ 运动层的路径耗时。报告输出可用疏散时间减去所需疏散时间的余量（EVAC_MARGIN），按住户分别给出。
- 参数在跑之前冻结，只用来比较不同住户之间、以及改造前后的差别，不给出绝对时间结论。
- 交互原型的火灾实验（§18）只作前端表现参考，T5 的结论以本节模型为准。

### 8.5 L3 MuJoCo 回放

- 从 IR 生成 MJCF：墙和门用盒体，家具用包围盒，演示户型里的家具用 CoACD 凸包。
- 轮椅是一个带 x 滑轨、y 滑轨、z 铰链的刚体，由位置执行器跟随 L1 路径。
- 记录接触对（映射回物体 id）、接触力、穿透深度。
- 离屏渲染先试 `MUJOCO_GL=egl`，不行再试 `osmesa`。两者都不行，就把接触数据导出给网页前端显示。

## 9. M7 修复 Agent

### 9.1 编辑原语和代价

| 代价 | 编辑 | 约束 |
|---|---|---|
| 1 | 平移家具（沿墙或在房间内，步长 0.10 m，最多 1.0 m） | 不穿墙、不和其他物体重叠；编辑前靠墙的仍然要靠墙；不能挡住其他门、窗 |
| 1 | 旋转家具 90° 或 180° | 同上 |
| 2 | 删除非必需物体（装饰、椅子、边几、地毯） | 房间功能不丢：卧室要有床，卫生间要有马桶，厨房要有灶台 |
| 3 | 换同类商品（从资产库选尺寸更小或台下净空更大的款） | 只能从已入库的资产里选；新物体同样要满足摆放约束 |
| 3 | 加辅具（床边扶手、马桶扶手） | 只放在交互区边缘，不占通道 |
| 4 | 门改开向，或平开改推拉 | 推拉门要求门侧墙面有足够长度 |
| 6 | 门加宽 | 只在其他编辑都无效时考虑 |

### 9.2 搜索

1. 从违规报告里取出所有失败任务的阻挡物体，作为候选目标。
2. 对每个目标枚举上表中可行的编辑，在单个编辑的层面先过约束检查。
3. 以"失败任务数、红色违规数、编辑总代价"做字典序目标，做最佳优先搜索。每个候选都完整重跑 M5/M6，最多组合 3 个编辑。
4. LLM 只做两件事：给候选编辑排序（作为启发，决定先试哪个），以及把最终方案写成改造建议文字。是否采纳以重跑结果为准。
5. 输出：编辑清单、每个编辑的前后指标、总分变化。所有改动对**所有住户**重新评估。修好轮椅的问题，不能让助行器使用者的任务变差。

### 9.3 方案演化模块（Evolver，P2）

§9.2 沿一条路径找到一个方案就停。方案演化模块同时维护一批候选方案：LLM 在较好的方案上改出新方案，仿真当评估器打分，逐代筛选。循环结构参照 LLM 驱动的演化搜索框架（AlphaEvolve 一类）：选择 → 生成 → 评估 → 反馈，种群分岛。代码在 `src/ha/repair/evolve.py`。

同一个循环有两种用法：

| | 方案模式 | 策略模式 |
|---|---|---|
| 个体 | 一套户型的改造方案：编辑清单（§9.1 原语），或整屋布局 | 通用修复启发函数 `propose(scene_ir, report, persona) -> ranked edits` 的代码 |
| 评估 | 对这套户型的所有住户 × 适用任务重跑 M5/M6 | 在一批注入缺陷的户型上跑 §9.2 搜索，用它替换第 4 步的 LLM 排序 |
| 适应度 | 字典序（失败任务数、红色违规数、编辑总代价）；任一住户变差或违反约束判为不可行 | 修复成功率 − 0.05 × 平均编辑代价；违反约束判 0 |
| 产出 | 几套彼此不同的方案（例如"花钱最少""效果最好"）给用户挑 | 一个可复用的启发函数，用于批量体检 |
| 谁调用 | A8 修复、A5 整屋布局（E16） | E10、M9 批量 |

每一代：

1. **选择**：从种群里挑父代。保留精英；按编辑类型和目标物体聚类，每类都抽，避免种群收敛到同一种改法；留少量随机名额。
2. **生成**：LLM 读父代方案和它的违规报告，做变异（改一个编辑、换目标物体、换商品）或交叉（合并两个方案里互不冲突的编辑）。新方案先过 §9.1 的约束检查，不通过的不进评估。
3. **评估**：调用评估器（A7），结果确定。方案按内容哈希缓存，同一方案不重复跑。
4. **反馈**：把失败原因（哪个住户、哪个任务、卡在哪个物体、差多少）写回个体，作为下一代生成的提示。
5. **种群**：默认 3 个岛独立演化，每隔几代按环形把最优个体迁到下一个岛；连续多代不提升的岛重置。

规则：

- 分数只来自评估器，LLM 只出候选，和 §9.2 一样。
- LLM 只拿到方案和违规报告的结构化摘要，不拿户型原始文件。
- 每次运行的评估次数上限在冻结计划里事先写好。LLM 不可用时，生成步退回随机变异，循环照常跑。
- 对照组：随机搜索、§9.2 的规则排序最佳优先搜索，评估次数相同。
- 策略模式的数据划分见 §15；方案模式只针对单套户型，不报跨户型结论。
- 演化曲线和对照结果写进 manifest；没过门的结果不进主结论。

## 11. M9 规模化（评测模式）

M9 是产品评测模式（prd §2.3、F8）的计算后端。

- 500 套全部跑 M1 导入，以及 3 个画像 × T1–T4 的 L0–L2，按户型分片并行（`--shard i/n`），多核 CPU 机器即可（比赛计划 E9）。
- 输出达标率分布、失败原因 Top 5、按房间类型的问题分布，作为视频里的规模化镜头。处理失败的户型单独列出，不从分母里去掉。
- **成对比较**：实验配置指定一个变量（家具系列、门净宽、走廊宽、床侧留空）和取值，其他条件固定。同一套住宅、同一个住户只换这个变量各跑一次，输出变好、变差、不变的住宅数。家具系列评测是把同一类家具整体换成某个系列的商品（`catalog.yaml`），按商品尺寸用布局求解（agent-backend §9）重新落位。
- 实验配置（场景清单、画像参数、变量、种子）写进 run 的 manifest，同一配置重跑汇总表完全一致。
- 这一步不跑 LLM，只用规则策略，所以结果确定，成本也低。
- SAGE-10k 是单房间场景（[data §7](data.md)），只用于单房间批量测试；按户型分布生成整套住宅放在比赛之后。

## 13. 技术要点

1. **规范可执行化**：GB 55019、GB 50763 和 ADA 条文变成可计算的检查，每条违规落到物体 id 和差值。
2. **按真实外形规划**：矩形轮椅外形加非完整约束的 SE(2) 规划，加分层占用（脚踏能进台下）。同一扇门可以直接对比圆盘模型和矩形模型的结论差异。
3. **软碰撞归因**：没有无碰撞路径时，用最小穿透路径回答"会撞在哪里、撞多深"。
4. **双层数字住户**：LLM 只在运动层给出的候选里选，独白要和真实数字对得上，分数只来自运动层。
5. **验证式修复**：按编辑代价搜索，每个方案都对所有住户重新仿真，避免顾此失彼。
6. **资产按需入库**：商品图经 Lux3D 生成，校准尺寸，加铰接和凸分解后直接进入仿真。
7. **多风险叠加**：同一套 IR 上叠加夜间照度、烟气疏散的示意分析，再加担架通行（换外形复用规划器）和杂物容错（逐步加障碍测余量）。

## 14. 风险与降级

| 风险 | 降级办法 |
|---|---|
| 门净宽测量不准 | 演示户型的门人工核对；批量统计里标注测量方法 |
| 房间多边形合并失败 | 退回用地面网格的包围盒，并在报告里标注 |
| Hybrid-A* 太慢 | θ 降到 16 档，或者栅格放粗到 0.08 m |
| LLM 端点不可用或输出不稳定 | 切换到规则策略，独白改用模板句 |
| Lux3D 生成质量差或 QA 门不过 | 换图重试 1 次；仍不过就用包围盒加商品图贴片代替 |
| MuJoCo 离屏渲染不可用 | 只导出接触数据，在网页里显示 |
| GLB 材质丢失 | 按类目统一上色 |
| 网页录屏失败 | 用俯视 mp4 动画代替 |

## 15. 评估器自检与防作弊

评估器必须确定、可复现、冻结后不改，因为修复和方案演化的分数全部来自它。

**自检**（对应比赛计划 E2、E3）：

- 缺陷注入（E2）：在非演示户型里抽 20 套，注入已知缺陷（门缩到 0.70 m、转身区放 0.6 × 0.6 m 箱子、吊柜下沿抬到 1.60 m），检查召回率和原因归属，要求召回 ≥ 0.9、归属正确率 ≥ 0.9。
- 误报抽查（P2）：对判失败的原始户型抽 30 套人工看平面图，误报 ≤ 10%。
- 对照组（E3）：步行对照在适用任务上成功率 ≥ 90%，达不到时先排查评估器。
- 确定性：同一输入重跑两次，结果 JSON 逐字节一致；不依赖随机人群。

**防作弊**：

- 评估器代码和阈值文件冻结时记录哈希，写进每次运行的 `manifest.json`。
- 方案演化的策略模式只在 dev 上打分，val 用来选程序，holdout 只用一次（划分见 [data.md §5](data.md)）。
- 门没过就记为 REJECTED，修代码缺陷，不改阈值、不换种子、不删失败的 run。
- 最终方案在 L3 物理回放里再过一遍。

## 16. 物理仿真与算力

| 用途 | 引擎 | 说明 |
|---|---|---|
| 评分 | 不用物理引擎 | L0–L2 是栅格和 SE(2) 几何计算，确定、快，CPU 即可 |
| 接触复核（L3） | MuJoCo | DeepMind 开源，Apache-2.0，`pip install mujoco`，CPU 运行，笔记本上也能跑。读 IR 生成的 MJCF，按 L1 路径回放，输出接触点和穿透深度（§8.5） |
| 展示镜头、人形动画（可选） | Isaac Sim | 需要 RTX 显卡（A100、H100 这类数据中心卡没有 RT 核，不适用），有 RTX 算力的队友才跑。WSR 本身是带 PhysX 关节的 USD，可以直接加载；画面和铰接门、柜的效果好于 MuJoCo |
| 展示镜头兜底 | Blender | 读展示用 GLB 和 L1 轨迹，Cycles 或 EEVEE 离线渲染，CPU 可跑，可以多进程批量出帧 |

这些引擎都不参与打分。展示镜头的主线是网页 3D 回放；需要更好的离线画面时，有 RTX 用 Isaac Sim，没有就用 Blender。

每个阶段开跑前在 `plans/` 写冻结计划：假设、阈值、数据划分、成功门、停止条件。比赛期间的实验 E0–E16 是这几个阶段的缩小版，门写在[比赛计划 §7](../../plans/hackathon-plan.md)。

## 18. 交互原型 `prototypes/indoor-space-interaction/`

浏览器端原型（Three.js r128，无构建），依赖 `prototypes/js/vendor/three-r128/`，运行方法见仓库 README。原型包括：

- “自由探索”：圆盘人群、栅格 Dijkstra、碰撞热力。
- “灾害实验”：确定性的火灾传播场（温度、燃料、烟气、风向、墙体阻断）和地震损伤模型（累计结构损伤、倒塌碎片用 cannon-es 刚体），行人按危险代价改道。
- 导入：支持 USDZ，本机 OpenUSD 转成 GLB 后载入，WSR 的 `scene*.usdz` 可以直接打开。
- “任务驱动数字住户”：4 个画像（轮椅、助行器、视障白杖、上肢受限）和 5 项任务（入户到沙发、卧室到卫生间、取用冰箱、床椅转移、紧急疏散）。这组画像是原型自带的，参数与本方案的画像（§6）不同，原型没有步行对照。位置加 8 个朝向的搜索，平移和转向都检查矩形扫掠，允许倒退；开门检查接近、触达、阻力、门扇扫掠和退让位置。另有规则修复候选（挪家具、换低位把手冰箱、改开门方向），每个候选重跑同一任务集。

| 原型部分 | 在本方案中的用法 |
|---|---|
| 三维前端、热力层、栅格详情面板、行人视角、任务住户界面 | 复用为 `web/` 的起点，改成读评估器输出的 IR、轨迹和违规 JSON |
| `access-lab/1` 导出的原因字段 | 参考违规报告格式（§8.2） |
| `core.js` 的距离变换、按半径连通、Dijkstra | 思路复用为 L0 预筛，用 Python 重写 |
| `geometry.js` 的三角面高度带裁剪 | 借鉴为分层占用（§3）；固定的 0.08–1.80 m 高度带改成 4 层 |
| 原型自己的住户判定和修复 | 只做演示和交互参考，不进评分。分数只来自 `src/ha/evaluator`，画像参数以 `personas.yaml` 为准 |
| 随机人群和按本次最大值归一化的热力 | 不用于评分，结果随人群随机 |
| 火灾、地震实验 | 只作前端表现和行为调试，不进评分；T5 以 §8.4 为准 |
| `scripts/convert_usdz.py` 的 USDZ 转 GLB | 后端转换接口照此实现（agent-backend §10.1）；评估器仍从 USD 直接导入（§3），不读这份 GLB |
